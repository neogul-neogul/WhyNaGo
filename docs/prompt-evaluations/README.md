# 서술형 프롬프트 비교

서술형 채점·꼬리질문 프롬프트의 품질을 같은 입력으로 비교하고, 실제 모델 응답을 Markdown으로 보관한다.

**한 번의 실행은 언제나 두 프롬프트만 비교한다.** 기준선 하나와 후보 하나다. 세 개 이상을 한 리포트에 담으면 어떤 변경이 어떤 점수 차이를 만들었는지 귀속시킬 수 없기 때문이다. 기준선은 보통 후보의 직전 버전으로 두고, 여러 버전을 보고 싶으면 쌍을 바꿔 여러 번 실행한다.

비교하려면 두 버전이 `GradeAndFollowupResult` 형식(`feedback`, `modelAnswer`, `score`, `followupQuestion`, `mastery`, `masteryReason`, `criteriaResults`)을 공유해야 한다. `v1`~`v5`는 형식이 달라 비교할 수 없다.

## 실행

로컬 Ollama 서버와 모델이 필요하다. 기본 모델은 `gemma3:4b`이며, 다른 설치 모델은 `OLLAMA_MODEL`로 바꿀 수 있다.

```bash
OLLAMA_MODEL=gemma3:4b ./gradlew promptEvaluation
```

일반 `./gradlew test`는 외부 모델 호출을 하지 않는다. `promptEvaluation`만 실제 생성 모델 호출과 LLM 심사를 수행한다.

실행할 때마다 기존 결과를 덮어쓰지 않고 다음 형식의 새 파일을 저장한다.

```text
eval_v7_v8_20260820-134932.md
```

파일명은 기준선·후보 버전과 실행 시각(`yyyyMMdd-HHmmss`)으로 구성된다.

## 비교 대상과 골든셋

- 비교 대상은 `src/test/java/com/neogul/whynago/question/infra/ai/promptevaluation/PromptEvaluationCatalog.java`의 `comparison()`에 등록한다. 기준선, 후보, 그리고 **두 프롬프트의 핵심 차이** 세 가지를 바꾼다.
- 핵심 차이는 사람이 직접 쓴다. 프롬프트 문구를 그대로 옮기지 말고, 그 변경이 **응답에서 어떤 차이로 나타나야 하는지**를 쓴다. 심사 모델이 응답만 보고 확인할 수 있는 말이어야 한다.
- 카탈로그는 실행 전에 같은 버전끼리의 비교, 기준선보다 이전인 후보, `v6` 미만 버전, 비어 있는 핵심 차이를 거부한다.
- 입력 케이스는 `src/test/resources/prompt-evaluation/cases.json`에서 관리한다. 한 케이스에는 질문, 사용자 답변, 채점 모드, 루브릭, 꼬리질문 범위, 소요시간, 사람이 작성한 기대 기준을 넣는다.
- 새 프롬프트는 같은 출력 형식을 지켜야 한다.

골든셋은 한 가지 답변 수준에 치우치지 않게 정답·부분 정답·오답·모름 답변, 루브릭 유무, 빠름·보통·느린 소요시간, 꼬리질문 범위 제한을 포함하는 것을 권장한다.

## 리포트 읽는 법

리포트 맨 위에는 이번 실행이 비교하는 두 버전과 **두 프롬프트의 핵심 차이**가 실린다. 점수보다 이것을 먼저 읽는다. 심사 점수 자체가 이 차이를 기준으로 매겨졌기 때문이다.

각 케이스는 먼저 `평가 입력` 표로 질문과 사용자 답변, 루브릭, 기대 기준을 보여 준다. 그 다음 표는 행이 응답 필드이고 열이 프롬프트 버전이므로 같은 필드를 버전별로 바로 비교할 수 있다.

| 영역 | 확인할 내용 |
| --- | --- |
| `feedback` | 틀리거나 빠진 내용을 정확히 짚고 다음 학습 대상을 구체적으로 제시하는지 |
| `modelAnswer` | 질문에 정확히 답하고 필요한 근거를 담는지 |
| `score`·`criteriaResults` | 루브릭 항목 판정과 배점 합이 일치하는지 |
| `mastery`·`masteryReason` | 답변 내용과 소요시간을 근거로 숙련도를 일관되게 판정하는지 |
| `followupQuestion` | 직전 문답을 기반으로 한 단계만 깊어지며 허용·금지 범위를 지키는지 |

`criteriaResults`는 배열을 들여쓴 JSON 형태로 렌더링해 각 `index`, `met`, `reason`을 읽을 수 있게 한다.

`심사 결과`는 응답 비교 표와 분리되어 있다. 심사 모델에는 위의 핵심 차이를 그대로 주고, 그 차이가 응답에 실제로 나타났는지를 중심으로 채점하게 한다. **어느 버전의 응답인지는 알려 주지 않는다** — 알려 주면 후보라는 이유만으로 점수가 올라간다. 심사 모델은 아래 8개 축을 각각 1~5점으로 매기고 짧은 근거를 남긴다.

| 심사 축 | 의미 |
| --- | --- |
| 채점 정확성 | 답변의 정확성·오개념·이해 수준을 올바르게 판단했는지 |
| 루브릭/점수 일관성 | 루브릭 판정과 점수의 근거가 맞는지 |
| 피드백 | 구체적이고 다음 학습에 도움이 되는지 |
| 모범답안 | 정확하고 질문에 충분히 답하는지 |
| 꼬리질문 관련성 | 직전 문답에서 벗어나지 않는지 |
| 꼬리질문 난이도 | 답변자 수준에서 한 단계 깊어지는지 |
| 꼬리질문 가드레일 | 금지 개념·범위 제한을 지키는지 |
| 차이 반영 | 위에 적은 핵심 차이가 이 응답에서 실제로 나타나는지. 응답의 좋고 나쁨이 아니라 그 차이가 보이는지만 본다 |

요약 표의 `<기준선> 대비`는 같은 케이스에서의 심사 총점 차이다. 점수 차이만으로 승자를 확정하지 말고, 필드별 응답과 계약 검사 결과를 함께 확인한다. 특히 `차이 반영`이 기준선과 후보에서 어떻게 갈리는지가 그 변경이 실제로 먹혔는지를 가장 직접적으로 보여 준다.

## 계약 검사와 실패

평가 하네스는 LLM 심사와 별도로 아래를 결정적으로 검사한다.

- 필수 응답 필드 존재 여부와 `score` 범위(0~10)
- 꼬리질문 생성 여부에 따른 `followupQuestion` 존재/`null` 여부
- `mastery`와 `masteryReason` 존재 여부
- 루브릭 `criteriaResults`의 항목 번호·개수와 `score`의 배점 합 일치 여부
- 꼬리질문 금지 범위의 직접 언급 여부

한 조합의 호출이 실패해도 비교 전체가 날아가지 않는다. 생성·심사는 각각 3회까지 다시 부르고, 그래도 실패하면 그 칸만 실패로 기록한 뒤 나머지 비교를 계속한다.

계약 위반이 있으면 Gradle 태스크는 실패한다. 그러나 비교 결과를 분석할 수 있도록 리포트는 실패 전에 저장된다. 따라서 실패한 실행의 Markdown도 삭제하지 말고, 어떤 버전에서 어떤 필드가 어긋났는지 확인하는 근거로 사용한다.
