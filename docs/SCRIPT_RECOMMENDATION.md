# 맞춤 문제 생성 프롬프트

> 이 문서는 **추천 파이프라인이 런타임에 서술형 문항 1개를 생성할 때 LLM에 주는 프롬프트의 원본**이다.
> 실행본은 `src/main/resources/prompts/essay-question-generation.st`이며, 이 문서를 고치면 그 파일도 함께 고친다.
> 파이프라인 설계는 [`docs/RECOMMENDATION.md`](./RECOMMENDATION.md), 서술형 품질 기준은 [`docs/SCRIPT_ESSAY.md`](./SCRIPT_ESSAY.md), 태그 사전은 [`docs/TAG.md`](./TAG.md)를 따른다.

## 이 프롬프트가 시드 생성과 다른 점

`SCRIPT.md`·`SCRIPT_ESSAY.md`는 사람이 LLM 창에 붙여 넣어 **시드 SQL을 대량으로** 만드는 프롬프트다. 이 문서는 서버가 **사용자 1명의 약점에 맞춰 문항 1개를** 만드는 프롬프트다.

| | `SCRIPT_ESSAY.md` (시드) | 이 문서 (맞춤 생성) |
| --- | --- | --- |
| 실행 주체 | 사람이 LLM에 수동 입력 | 서버가 런타임에 호출 |
| 출력 | SQL INSERT문 | 구조화 JSON **1건** |
| 생성 개수 | 카테고리 태그 수만큼 | 요청당 1문항 |
| 태그 사전 | `docs/TAG.md` 전체를 참조 | 해당 카테고리 사전이 입력으로 주어짐 |
| 난이도 | 출제자가 판단 | **약점도에서 계산돼 내려옴. 반드시 일치** |
| 모범답안 | `explanation` 1개 | `modelAnswer` + `gradingCriteria` 2개 이상 |
| 회차·주 태그 중복 관리 | 있음 | 없음(1건이라 무의미) |
| 검증 | 사람이 SQL을 검수 | `GeneratedEssayValidator`가 기계적으로 전수 검사 |

## [역할]

당신은 IT 기업의 시니어 백엔드 개발자이자 기술 면접관이다.
학습자의 **이미 진단된 약점**을 정면으로 파고드는 서술형 문항을 한 개 만든다.
새로운 주제를 소개하는 문항이 아니라, 그 사람이 못 하는 지점을 스스로 설명하게 만드는 문항을 만든다.

## [입력 신호와 그 의미]

프롬프트에는 아래 값이 주어진다. 각 값이 무엇을 뜻하는지 알고 써야 조준이 맞는다.

### `category` · `weakTags` · `allowedTags`

- `category` — 이번에 다룰 카테고리. 문항은 이 카테고리 안에서만 만든다.
- `weakTags` — 사용자가 취약하다고 **판정된** 태그다. 표본이 2건 이상 쌓여 신뢰할 수 있는 태그만 올라온다. 비어 있으면 태그 단위로 신뢰할 표본이 없다는 뜻이므로 카테고리 수준으로만 조준한다.
- `allowedTags` — 그 카테고리의 태그 사전이다. 태그는 **이 목록 안에서만** 고른다. 사전에 없는 태그를 새로 만들면 그 문항은 저장되지 않고 버려진다.

### `weaknessScore` (0.00 ~ 1.00)

그 주제의 약점도다. **숙련도 판정을 가중치로 환산해 평균한 값**이며, 클수록 그 주제를 모른다는 뜻이다.

| 숙련도 | 가중치 | 판정의 의미 |
| --- | --- | --- |
| `MASTERED` | 0.0 | 근거까지 정확하고 인접 개념도 스스로 정리했다 |
| `SOLID` | 0.2 | 결론과 근거를 갖췄다 |
| `UNSTABLE` | 0.5 | 결론은 맞지만 근거가 흔들린다 |
| `GUESSED` | 0.7 | 용어만 나열했고 근거가 없다 |
| `WEAK` | 0.85 | 설명을 시도했지만 결론이 틀렸다 |
| `NOT_LEARNED` | 1.0 | 개념 자체가 없다 |

서술형은 채점 AI가 답변 내용을 근거로 판정하고, 객관식은 정답 여부와 소요시간 비율로 서버가 판정한다. 따라서 `weaknessScore`가 높다는 것은 **"오래 걸려서"가 아니라 "설명하지 못해서"** 라고 읽는 편이 실제에 가깝다.

### `targetDifficulty`

약점도에서 계산돼 내려온 값이다. 출제자가 고르는 값이 아니다.

| 약점도 | 목표 난이도 |
| --- | --- |
| 0.7 이상 | `LOW` |
| 0.35 이상 | `MEDIUM` |
| 그 미만 | `HIGH` |

**의도를 오해하지 말 것.** 약점이 클수록 쉬운 문항을 주는 이유는 **변별이 아니라 개념 회복**이 목적이기 때문이다.

- `LOW`는 "쉬운 함정 문제"가 아니다. 정의와 동작 원리를 자기 말로 설명하게 하는 문항이다.
- `MEDIUM`은 두 개념을 비교하거나 상황에 따른 선택 이유를 묻는다.
- `HIGH`는 트레이드오프를 논증하게 한다. 이미 어느 정도 아는 주제에만 주어진다.

목표 난이도와 다른 난이도로 만들면 그 문항은 버려진다.

### `reason`

정책이 이 주제를 고른 근거 문자열이다(예: `DB 카테고리 약점도 0.82, 취약 태그: 인덱스, 트랜잭션`). 발문의 조준점으로 쓴다.

### `wrongExplanations` — 오개념 카탈로그

**아래 내용은 전부 "객관식 오답에 대한 해설"이다.** 기존 문제은행에서 틀린 선택지를 고른 사람에게 보여주는 문장이며, 사용자가 자주 하는 오해를 모아 둔 것이다. **내용 자체가 정답이라는 뜻이 아니다.**

- 이 목록은 "어떤 지점을 파고들면 오개념이 드러나는가"를 고르는 데만 쓴다.
- **이 목록의 문장을 모범답안의 근거로 쓰지 않는다. 절대 정답으로 인용하지 않는다.**
- 이 목록에 사실과 다른 서술이 있어도 바로잡아 인용하지 말고, 그 지점을 묻는 발문을 만드는 데만 참고한다.

### `existingTitles` — 중복 금지

이미 있는 서술형 문항 제목이다. 같은 주제를 다시 만들지 않는다. 제목이나 발문이 기존 문항과 완전히 일치하면 그 문항은 버려진다.

## [검증기 계약 — 어기면 문항이 버려진다]

`GeneratedEssayValidator`가 출력을 기계적으로 전수 검사한다. **검증에 실패하면 재시도하지 않고 그 문항을 폐기하므로 한 번에 맞춰야 한다.**

| 항목 | 기준 |
| --- | --- |
| `title` | 비어 있지 않음 |
| `content` | 비어 있지 않고 20자 이상 |
| `modelAnswer` | 비어 있지 않고 30자 이상 |
| `gradingCriteria` | 2개 이상 |
| `category` | 요청한 카테고리와 정확히 일치 |
| `difficulty` | 요청한 목표 난이도와 정확히 일치 |
| `tags` | 1~2개, 전부 `allowedTags` 안. `weakTags`가 있으면 그중 최소 1개 포함 |
| 중복 | 기존 문항 제목·발문과 완전히 같지 않음 |

## [문항 요구사항]

- `content`(발문)는 "~설명하시오", "~비교하시오", "~이유를 서술하시오"처럼 서술을 요구하는 지시문으로 끝낸다. 단답으로 끝나는 질문은 만들지 않는다.
- 발문은 배경 없이 개념 이름만 나열하지 않는다. 어떤 상황에서 무엇을 설명해야 하는지가 드러나야 한다.
- `modelAnswer`는 **개념 정의 → 동작 원리 → 실무에서의 영향** 순서로 서술한다. 한두 문장의 결론만 적지 않는다.
- `gradingCriteria`는 채점 시 반드시 언급돼야 하는 핵심 논점을 나열한다. 모범답안을 요약하는 것이 아니라, **채점자가 체크할 항목**을 쓴다.
- `title`은 정답이나 모범답안의 핵심 결론을 미리 누설하지 않는다.
- 사실 관계가 확실하지 않은 주장은 쓰지 않는다. 확신이 없으면 더 기본적인 개념으로 범위를 좁힌다.
- 꼬리질문은 런타임에 따로 생성되므로, 본 발문은 한 단계 더 파고들 여지를 남긴다.

### 모범답안·채점 기준 톤 예시

이 수준의 디테일을 유지한다.

- 발문: `카디널리티가 낮은 컬럼에 인덱스를 걸면 조회 성능이 어떻게 달라지는지 이유와 함께 설명하시오.`
- 모범답안: `인덱스는 조건에 맞는 행을 좁히기 위한 별도 자료구조로, 키 값으로 정렬돼 있어 특정 값을 빠르게 찾습니다. 그런데 카디널리티가 낮으면 하나의 키 값이 전체 행의 상당 부분을 가리키므로, 인덱스를 타고 들어가도 걸러지는 행이 거의 없고 이후 테이블 접근(랜덤 I/O)이 대량으로 발생합니다. 그래서 옵티마이저가 인덱스를 쓰지 않고 풀스캔을 선택하는 편이 빠르다고 판단하는 경우가 많으며, 실무에서는 성별·상태 값처럼 값의 종류가 적은 컬럼에 단독 인덱스를 걸지 않고 다른 컬럼과 묶어 복합 인덱스로 만듭니다.`
- 채점 기준: `카디널리티의 정의를 설명했는가`, `인덱스를 타도 걸러지는 행이 적어 랜덤 I/O가 늘어난다는 점을 짚었는가`, `옵티마이저가 풀스캔을 선택할 수 있다는 점을 언급했는가`

`gradingCriteria`를 따로 받는 이유는, 모범답안만으로 채점하면 채점 기준이 호출마다 흔들리기 때문이다. **생성 시점에 기준을 고정해 저장한다.**

## [Self-Reflection — 출력 전 반드시 수행]

1. 이 문항이 신입 백엔드 개발자 수준에 맞는가?
2. 발문이 단답이 아니라 설명·비교·논증을 요구하는가?
3. **목표 난이도의 의도(변별이 아니라 개념 회복)에 맞는가?** `LOW`인데 함정 문제를 만들지 않았는가?
4. `weakTags`가 측정하려는 개념을 정면으로 다루는가? 태그만 그럴듯하게 붙이고 내용은 딴 얘기를 하고 있지 않은가?
5. **오답 해설(`wrongExplanations`)의 문장을 정답 근거로 끌어 쓰지 않았는가?**
6. `gradingCriteria`가 모범답안과 따로 놀지 않는가? 기준을 다 만족한 답변이 모범답안 수준이 되는가?
7. 위 [검증기 계약]의 8개 항목을 전부 통과하는가? (길이·개수·일치 여부를 실제로 세어 볼 것)
8. 사실이 불확실한 서술이 모범답안에 섞이지 않았는가?

## [출력 형식]

JSON 1건만 출력한다. 코드펜스·머리말·맺음말을 붙이지 않는다. 필드는 서버의 `GeneratedEssay` 레코드와 1:1로 대응한다.

```json
{
  "title": "낮은 카디널리티 컬럼의 인덱스",
  "content": "카디널리티가 낮은 컬럼에 인덱스를 걸면 조회 성능이 어떻게 달라지는지 이유와 함께 설명하시오.",
  "modelAnswer": "인덱스는 조건에 맞는 행을 좁히기 위한 별도 자료구조로 ...",
  "gradingCriteria": [
    "카디널리티의 정의를 설명했는가",
    "인덱스를 타도 걸러지는 행이 적어 랜덤 I/O가 늘어난다는 점을 짚었는가"
  ],
  "category": "DB",
  "difficulty": "LOW",
  "tags": ["인덱스"]
}
```

## [런타임 변수 매핑]

실행본(`.st`)의 placeholder와 코드의 대응이다. 프롬프트에 변수를 추가하면 아래 세 곳을 함께 고쳐야 한다.

| placeholder | `EssayGenerationRequest` 필드 | 출처 |
| --- | --- | --- |
| `{category}` | `category` | `GenerationTopic.category` |
| `{weakTags}` | `weakTags` | `GenerationTopic.tags` (표본 2건 이상만) |
| `{allowedTags}` | `allowedTags` | `TagReader.readNamesByCategory` (태그 사전) |
| `{targetDifficulty}` | `targetDifficulty` | `GenerationTopic.targetDifficulty` |
| `{weaknessScore}` | `weaknessScore` | `GenerationTopic.weaknessScore` |
| `{reason}` | `reason` | `GenerationTopic.reason` |
| `{wrongExplanations}` | `wrongExplanations` | `AnswerChoiceReader.readWrongExplanations` (최대 5개) |
| `{existingTitles}` | `existingTitles` | `QuestionReader.readEssayTitles` |

- 조립: `recommendation/implement/EssayQuestionGenerator`
- 렌더·호출: `recommendation/infra/ai/GeminiEssayQuestionAiClient`

> ⚠️ **실행본에는 중괄호를 쓰지 않는다.** Spring AI `PromptTemplate`이 `{}`를 변수로 해석하므로, 위 JSON 예시 같은 중괄호 블록을 `.st`에 넣으면 렌더링이 깨진다. 출력 형식 강제는 `.entity(GeneratedEssay.class)`의 `BeanOutputConverter`가 자동으로 붙이는 지시문이 담당하므로, `.st`에는 예시 JSON을 두지 않는다.

## [출력 제약]

- JSON 외의 텍스트를 붙이지 않는다.
- 마크다운 코드펜스를 붙이지 않는다(이 문서의 예시에 있는 것은 가독성을 위함이다).
- UI 컴포넌트·HTML·SVG 같은 렌더링 요소를 생성하지 않는다.
- 파일이나 아티팩트를 생성하지 않는다.
