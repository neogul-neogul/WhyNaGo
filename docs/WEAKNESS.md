# **취약점 탐지 전략 — 숙련도 세분화와 태그 벡터**

## **목표**

이 문서는 **"진짜 취약점"을 어떻게 찾을지**를 남기는 전략 문서다. 결정과 그 근거, 아직 못 정한 것과 알고 있는 리스크를 적는다. 무엇을 언제 구현했는지는 git 로그를 본다.

지금은 숙련도를 6분류로 판정하고 그 가중치 평균을 정렬해 취약 태그를 고른다(`docs/RECOMMENDATION.md`의 "약점 프로필 정책"). 이 문서는 그것을 **태그별 숙련도 벡터 + 태그 간 의미 유사도 그래프**로 바꿔, 점수 정렬이 아니라 **약점의 성격을 분류**하는 방향을 다룬다.

추천 파이프라인 전체는 `docs/RECOMMENDATION.md`, 레이어 구조는 `docs/ARCHITECTURE.md`, 태그 사전은 `docs/TAG.md`, 검증용 페르소나 데이터는 `docs/SCRIPT_PERSONA.md`를 따른다.

## **판별 결과**

**타당하다.** 단, 세 가지를 먼저 바로잡아야 한다.

### **1. 가치를 만드는 것은 사용자 벡터가 아니다**

사용자의 태그별 숙련도를 238차원 벡터로 저장해도, **그 벡터를 정렬하는 것은 지금 하는 일과 수학적으로 동일하다.** 정보를 추가하는 것은 벡터에 곱할 **구조** — 태그 간 의미 유사도 그래프 — 이다.

| | 사용자 숙련도 벡터 | 태그 의미 임베딩 그래프 |
| --- | --- | --- |
| 정체 | 사용자당 238차원 `(score, confidence)` | 태그당 1024차원, **사용자 무관·정적** |
| 생성 | 런타임 집계 | **오프라인 1회** |
| 기여 | 정렬해도 오늘과 동일 → **정보 0** | **정보를 만드는 유일한 축** |

사용자 벡터는 저장 대상이고, 태그 그래프가 판정을 만든다. 이 구분을 흐리면 "벡터화했는데 결과가 그대로"가 된다.

### **2. 인프라는 필요 없다**

238태그 × 1024차원 ≈ **1MB**다. 벡터 DB·`VECTOR` 컬럼(MySQL 8.0에는 없다)·ANN 인덱스 전부 불필요하다. 오프라인에서 238×238 코사인을 구워 태그당 상위 K 이웃만 리소스로 내보내면, 런타임은 **결정적 산술이고 AI 호출이 0회**다. 쿼터·지연·`spring.ai.model.embedding: none` 설정을 전부 그대로 둘 수 있다.

임베딩 도구는 이미 있다 — `tools/question-pipeline/similarity/embeddings.py`(Ollama `bge-m3`, `cosine()`, 캐시)가 문항 중복 탐지에 쓰이고 있다. 같은 것을 태그에 돌린다.

### **3. 기존 근거가 실측과 다르다**

`docs/RECOMMENDATION.md`의 "태그를 1급 축으로 쓰지 않는 이유는 태그당 표본이 1건 수준"이라는 근거는 낡았다. `data3.sql`을 직접 세면:

| 항목 | 실측 |
| --- | --- |
| 문항 수 | 600 |
| `question_tag` 쌍 | **1,506** (365는 INSERT 문 수였다) |
| 사용된 태그 | **207 / 238** (31개는 문항 0개) |
| 태그당 문항 수 | min 1 / **중앙값 6** / 평균 7.3 / max 27 (TCP) |

**문제은행은 희소하지 않다. 희소한 것은 사용자의 풀이 이력이다.**

40문항을 푼 사용자는 약 100개 태그 인스턴스를 ~70개 태그에 흩뿌린다 → 태그당 ≈1.4건 → 거의 모든 태그가 `TagWeakness.MIN_TRUSTED_SAMPLE = 2`에 미달 → **8개 카테고리 점수로 붕괴한다.** 즉 오늘의 태그 레이어는 사실상 "카테고리 점수를 이름만 바꿔 네 번 보여주는" 것이다.

이것이 이 작업의 진짜 명분이다. **보간의 기반을 8개 버킷에서 238개 노드로 올린다.**

### **이미 드러난 결함 하나**

`docs/SCRIPT_PERSONA.md`가 스스로 적어 둔 성질이다 — `GUESSED`(0.7) < `WEAK`(0.85)이므로 **오개념 태그는 조준에서 항상 밀리고, 문항 수를 늘려도 순위가 뒤집히지 않는다**(가중치 평균의 상한이 0.7). "빠르게, 확신을 갖고 틀린다"는 가장 선명한 학습 신호가 구조적으로 후순위인 것이다. 연속 점수화와 이웃 일관성 판정이 이걸 고친다.

## **숙련도 세분화**

두 축을 함께 쓴다. **레벨이 밴드를 정하고, 연속 신호가 밴드 안에서의 위치를 정한다.**

### **레벨 확장 — 6분류 → 10분류**

신규 레벨은 **"LLM이 두 문장으로 구별 기준을 쓸 수 있는가"** 를 통과한 것만 넣는다. 모든 레벨은 기존 6분류 중 하나를 `parent()`로 갖는다.

| 레벨 | parent | 답변이 보인 상태 | 기본 가중치 |
| --- | --- | --- | --- |
| `MASTERED` | MASTERED | 결론·근거 정확 + 인접 개념·예외까지 자발적으로 정리 | 0.00 |
| `SOLID` | SOLID | 결론 정확 + 필요한 근거 완비 | 0.15 |
| `SOLID_NARROW` ✚ | SOLID | 결론·근거는 맞지만 경계 조건·적용 범위를 언급하지 않음 | 0.28 |
| `UNSTABLE` | UNSTABLE | 결론은 맞고 근거 일부가 틀림 | 0.45 |
| `UNSTABLE_SHAKY` ✚ | UNSTABLE | 결론은 맞지만 근거가 대부분 틀렸거나 자기모순 | 0.58 |
| `GUESSED` | GUESSED | 핵심 용어만 나열, 근거 없음 | 0.70 |
| `WEAK` | WEAK | 설명을 시도했으나 결론이 틀림 | 0.82 |
| `MISCONCEIVED` ✚ | WEAK | **길고 자신 있게 설명했으나 인과가 뒤집혀 있음** | 0.88 |
| `NAME_ONLY` ✚ | NOT_LEARNED | 이름만 알고 내용이 전무 | 0.95 |
| `NOT_LEARNED` | NOT_LEARNED | 개념 자체가 없음 | 1.00 |

- **`MISCONCEIVED`가 이 확장의 핵심이다.** `docs/SCRIPT_PERSONA.md`가 이미 "무엇을 무엇으로 착각했는지를 지목하라"고 요구하는 신호이고, 인과 역전은 텍스트에서 판별 가능하며, 지금 `GUESSED`/`WEAK`에 섞여 조준에서 밀리는 케이스다.
- **객관식(규칙 트랙)은 6분류만 낸다.** `정답 여부 × 3 페이스` = 6칸이므로 10레벨을 만들 신호가 없다. **없는 해상도를 발명하지 않는다.** 객관식의 세분화는 아래 연속 점수로만 얻는다.
- **하위 호환은 `parent()`가 담보한다.** `GET /api/mastery`·프론트 라벨·`MasteryWeight`의 기존 계약은 parent 기준으로 계속 동작한다. 프론트에 새 라벨을 노출하는 것은 별건으로 분리한다.
- **선행 조건 — 판정 일관성을 먼저 측정한다.** 프롬프트를 고치기 전에 고정된 답변 30건에 같은 프롬프트를 3회씩 돌려 신규 레벨의 재현율을 본다. 재현율이 낮은 레벨은 **넣지 않고 parent로 되돌린다. LLM이 구별하지 못하는 레벨은 해상도가 아니라 잡음이다.**

### **연속 점수화 — `masteryScore ∈ [0,1]`**

**밴드를 넘지 않게 클램프하는 것이 불변식이다.** 정제된 점수가 다른 레벨을 뜻하는 일은 절대 없다. 그래서 프롬프트·API·프론트 계약이 안 깨진다.

지금 계산해 놓고 버리는 연속 신호를 쓴다.

| 신호 | 현재 상태 | 출처 |
| --- | --- | --- |
| 루브릭 항목별 met 가중치 비율 | **채점 시 계산하고 버린다** (가장 큰 미사용 신호) | `RubricGradingResolver` → `EssayEvaluation.rubricCriteria` |
| 서술형 점수 0~10 | 합격/불합격으로만 쓴다 | `essay_solved.score` |
| 원시 elapsed 비율 | 3개 버킷으로 뭉갠다 | `ElapsedPacePolicy` |
| 최근성 | **전혀 쓰지 않는다** (3개월 전 판정 = 오늘 판정) | `solved_at` (두 테이블에 이미 있어 신규 쿼리가 필요 없다) |

그리고 태그마다 점수와 **함께** `confidence ∈ [0,1]`(표본 수 + 최근성)을 낸다. 이 `(score, confidence)` 쌍이 6버킷보다 근본적으로 해상도가 높다.

> ⚠️ **캐시 파괴 주의.** `RecommendationCache`는 `profile.hashCode()`를 키로 쓴다. 연속 감쇠를 넣으면 활동이 없어도 매 요청 프로필 해시가 바뀌어 **영구 캐시 미스 → 매 요청 생성 → `RECOMMENDATION_AI_QUOTA_EXCEEDED`** 가 된다. 최근성 감쇠는 **일(day) 단위로만** 계산하고, 해시 전에 소수 둘째 자리로 양자화하는 `WeaknessProfileKey`를 반드시 함께 넣는다. 벡터와 무관하게 **연속 신호가 들어오는 순간 필수**다.

## **태그 임베딩 그래프**

### **태그 이름을 임베딩하지 않는다**

- `복합 인덱스 / 커버링 인덱스 / 클러스터드 인덱스`는 순수 표면형만으로 ~0.9가 나온다. 의미가 아니라 글자를 재는 것이라 정보가 없다.
- `락`·`뷰`·`조인` 같은 1~2음절 태그는 임베딩 입력으로 거의 퇴화한다.
- 가장 나쁜 것: `docs/TAG.md`가 **의도적으로 분리한** 개념(`OS 데드락` ↔ `DB 트랜잭션 데드락`, `OS 캐시와 지역성` ↔ `GENERAL_CS 캐시 전략`)을 이름 임베딩이 ~0.95로 다시 붙인다. 사전이 애써 나눈 축을 무너뜨리는 것이 **가장 유력한 실패 모드**다.

대신 **태그당 문서**를 만들어 임베딩한다.

```
"{category} / {name}" + 그 태그 문항 최대 8개의 title + content (+ explanation)
```

태그당 중앙값 6문항이므로 207개 태그에서 성립한다. `embeddings.py`의 `retriever()` 주석이 이미 같은 주장을 하고 있다("태그 이름이 아니라 문항 본문으로 재야 한다"). 문항이 없는 31개 태그는 이름+카테고리만으로 만들고 저신뢰로 표시한다 — **LATENT 대상으로는 쓰되 이웃 소스로는 쓰지 않는다.**

### **동시출현을 섞되 동급으로 두지 않는다**

실측: 동시출현 차수 중앙값 2(top-10을 채울 수 없다), 562개 엣지 중 카테고리를 넘는 것이 **0개**(이는 태깅 규칙의 산물이라 증거가 아니다). 그래서 정밀도 사전확률로만 쓴다.

```
sim(a,b) = 0.75 · cos(doc_a, doc_b) + 0.25 · min(1, cooc(a,b)/3)
   단, cos >= floor 인 엣지만 유지     # floor는 embeddings.py의 시드쌍 p99 방식으로 캘리브레이션
   v1에서는 카테고리 횡단 엣지를 top-10 중 2개 이하로 제한
```

전부 오프라인. 모델명·K·블렌드 가중치·생성일을 리소스 헤더에 남겨 재현 가능하게 한다.

### **테이블이 아니라 classpath 리소스에 둔다**

`src/main/resources/tag-neighbors.tsv`(약 10KB)로 내보낸다. 테이블로 두면 안 되는 이유는 프로드가 `ddl-auto: update` + `spring.sql.init.mode: never`라는 점이다 — `ddl-auto`가 **빈 테이블만 만들고** 아무도 시드 SQL을 실행하지 않아 스무더가 무음으로 no-op 한다. 닫힌 사전에서 파생된 238×10 정적 데이터는 아무도 마이그레이션하지 않는 테이블이 아니라 **jar 안**에 있어야 한다. 나중에 쿼리 대상이 되면 그때 테이블을 만든다.

## **취약점 판정 — 정렬이 아니라 분류**

```
raw[t]      = 1 - masteryScore[t]                        (직접 관측한 약점도)
conf[t]     = f(표본 수, 최근성)
smoothed[t] = Σ sim(t,u)·conf[u]·raw[u] / Σ sim(t,u)·conf[u],   u ∈ topK(t) ∪ {t}
```

`raw`와 `smoothed`의 조합으로 **약점의 성격을 분류한다.** 여기가 "단순 점수 정렬"과 갈리는 지점이다.

| 판정 | 조건 | 의미 | 오늘 가능? |
| --- | --- | --- | --- |
| `OBSERVED` | conf 높음, raw ≈ smoothed | 직접 확인된 약점 | O |
| `STRUCTURAL` | smoothed 높음, 이웃도 일제히 약함 | **개념 구멍 — 진짜 취약점** | 카테고리 단위로만 |
| `INCIDENTAL` | raw 높지만 이웃은 강함 | **우연한 오답 하나 — 노이즈** | ✗ (지금은 1위로 올라온다) |
| `LATENT` | conf ≈ 0, 이웃이 약함 | **아직 안 풀었지만 취약할 것** | ✗ (원리적으로 불가능) |

순위는 `smoothed` + `STRUCTURAL` 보너스로 정한다.

- **카테고리 폴백을 삭제하지 않는다.** conf ≈ 0 **이고** 이웃도 비었을 때의 최후 수단으로 남긴다.
- **결정성** — 가중합을 `HashMap` 순회로 계산하면 부동소수 말단 비트가 흔들려 tie-break과 캐시 키가 뒤집힌다. 이웃은 `(-similarity, name)` 고정 순서로 순회하고 비교 전에 라운딩한다.
- **fail-open이 협상 불가다.** 그래프 리소스가 없거나 비면 `log.warn` 후 오늘과 동일한 산술로 강등한다. 시작 실패도, 무음 0도 안 된다.

> ⚠️ **중복 태그 위험.** `인덱스`의 최근접 이웃은 `복합 인덱스 / 커버링 인덱스 / 클러스터드 인덱스 / 실행 계획`이다. 오답 하나가 넷 다로 번지면 `WeakTagAssembler`의 top-4가 **한 개념의 네 가지 이름**이 되어 지금보다 UX가 나빠진다. 이웃 클러스터당 최대 1개라는 다양성 규칙을 어셈블러에 **처음부터** 넣는다.

> ⚠️ **LATENT은 줄 문항이 있어야 한다.** 문항 0개 태그 31개가 LATENT로 올라오면 쿼터 소진 시 `FallbackQuestionReader`가 줄 게 없다. 승인 문항이 1개 이상인 태그만 LATENT 후보로 두고, 요청당 최대 1개, 단독으로 주제를 만들지 않는다.

## **검증 — 무엇을 증명할 수 있고 무엇을 못 하는가**

**"진짜 취약점이 맞다"를 증명할 수는 없다.** 정답 레이블이 없고 실사용자가 사실상 1명이다. 어떤 시뮬레이터를 쓰든 검증하려는 상관구조를 스스로 주입하게 되어 순환논증이 된다. 이 한계를 감수한다는 사실을 인지한 상태로 진행한다.

측정할 수 있는 것은 아래 순서다.

| 게이트 | 무엇을 시험하는가 | 통과 기준 |
| --- | --- | --- |
| **1. 이웃 목록 표면 타당성** (사람) | 의미 그래프에 실제 구조가 있는가 | 40태그 × 이웃 10개 = 400건 판정, **precision@10 ≥ 0.8** |
| **2. 레이블 없는 구조 검사** (자동) | 임베딩이 글자만 읽고 있지 않은가 | 실측 562개 동시출현 엣지 recall@10이 카테고리 내 무작위를 뚜렷이 상회. 카테고리 횡단 엣지 비율도 함께 리포트 |
| **3. 페르소나 복원** (핵심) | 설계된 약점을 탐지기가 복원하는가 | 아래 3케이스 |
| **4. LLM 판정 일관성** | 신규 레벨이 재현되는가 | 고정 답변 30건 × 3회 |
| **5. leave-one-out** (모니터링) | 스무딩이 카테고리 폴백을 이기는가 | 유의성 미달 예상 — 만들어 두고 누적 |

게이트 1이 미달이면 **거기서 멈추고 Java를 쓰지 않는다.**

### **페르소나 복원 시험이 준(準)정답을 만든다**

`docs/SCRIPT_PERSONA.md`의 명세는 **사람이 임베딩과 무관하게** 쓴다. 진짜 정답 레이블은 아니지만 순환은 아니다.

1. `OS=strong, ALGORITHM=average, NETWORK=weak, TCP=misconception` → NETWORK 계열이 상위로 오는가, **`MISCONCEIVED`가 `WEAK`에 밀리지 않는가**
2. **LATENT 시험** — 약한 카테고리에서 **일부 태그만 풀게** 하고, 안 푼 인접 태그가 LATENT로 올라오는지 본다. **오늘 시스템은 원리적으로 불가능한 판정이다.**
3. **INCIDENTAL 시험** — strong 카테고리에 오답 1건을 심고, 그 태그가 1위로 올라오지 **않는지** 본다. 오늘은 올라온다.

### **leave-one-out 설계**

태그 t의 풀이 s를 가리고 `weakness(t)`를 세 방식(오늘의 카테고리 폴백 / 이웃 스무딩 / 전역 평균)으로 예측해 실제 관측 가중치와 비교한다. MAE + 쌍별 순위 정확도, 부트스트랩 신뢰구간, K ∈ {5,10,20}·블렌드 가중치 스윕. 사용자 1명에서는 유의성에 도달하지 못하지만 순수 함수라 싸다.

## **단계**

게이트를 통과하지 못하면 다음 단계로 가지 않는다.

| 단계 | 내용 | 산출 |
| --- | --- | --- |
| **0** | 오프라인 그래프 생성·캘리브레이션. **Java 0줄** | `tools/question-pipeline/similarity/tag_profiles.py`, `tag_neighbors.py`, `run.py`의 `neighbors` 서브커맨드, `src/main/resources/tag-neighbors.tsv` |
| **1** | 순수 도메인 산술 (Spring·LLM 의존 0) | `TagNeighbor(Graph)`, `TagConfidence`, `MasteryScore`, `NeighborhoodSmoother`, `TagWeaknessKind`, `TagWeaknessClassifier`, `WeaknessProfileKey` + `MasteryLevel` 확장 |
| **2** | 배선. **플래그 기본 off** | `TagNeighborResourceReader`(infra), `TagNeighborConfig`, `TagScoreAggregator`(implement), `WeaknessProfileCalculator`·`WeakTagAssembler`·`RecommendationTopicPolicy` 수정 |
| **3** | 루브릭 항목별 결과 영속화 | 벡터가 전혀 필요 없는데 정보 획득은 가장 크다. 0단계와 독립이라 병행 가능 |
| **4** | 사용자 숙련도 벡터 영속화 | `user_tag_weakness` + `WeaknessSnapshotScheduler`(`QuestionStatScheduler` 직후) |

- **0단계의 캘리브레이션 리포트는 `duplicates.py`의 `calibrate`와 같은 형식**으로 낸다 — 커버리지, recall@K, 횡단 비율, 사람 판정용 덤프, `판정:` 한 줄. 그 도구가 이미 "⚠ 이 지표를 버려야 한다"를 출력하는 관례를 그대로 승계한다.
- **2단계는 프로드 동작을 바꾸지 않는다.** 플래그 off면 산술이 오늘과 완전히 동일해야 하고, 이는 테스트로 고정한다. `smoothedScore`·`kind`·`confidence`는 `GET /api/recommendations/weak-tags`에 **추가 필드로만** 노출하고 `weaknessScore`와 정렬은 그대로 둔다. 실제 사용자에서 무위험 side-by-side를 일주일 보고 나서 정렬을 바꾼다.
- **4단계는 알고리즘에 필요하지 않다.** 238태그 × 사용자 1명은 마이크로초다. 정당화는 두 가지뿐이다 — (a) 벡터를 저장한다는 요구 자체, (b) `WeaknessProfileCalculator`가 매 요청 사용자의 **전체** 풀이 이력을 시간창·페이징 없이 읽는 현재 구조를 없앤다. (b)는 실제 이득이지만 지금 규모에서 급하지 않다.

## **하지 않을 것**

- `VECTOR` 컬럼·pgvector·Milvus·Redis vector·ANN 인덱스 — 1MB 데이터에 불필요
- **런타임 임베딩 호출.** `spring.ai.model.embedding: none`을 모든 프로파일에 유지한다. 그래프는 로컬 Ollama `bge-m3`로만 굽는다(무료·재현 가능)
- `tag_neighbor` **테이블** (위 "classpath 리소스" 참고)
- 사용자-사용자 유사도·협업 필터링 — 실사용자가 1명이다
- 카테고리 레이어와 `MIN_TRUSTED_SAMPLE` 제거 — 최후 폴백으로 남긴다
- 스무더를 필수 경로로 만들기 — 항상 fail-open
- 프론트에 신규 10레벨 라벨 노출 — 별건

## **알려진 리스크**

1. **검증 불가능성** — 위 "검증" 절 첫 문단. 페르소나 복원은 준정답이지 정답이 아니다.
2. **이웃 오염** — 임베딩이 `docs/TAG.md`가 의도적으로 분리한 개념을 다시 붙이면, 표본이 실제로 있는 유일한 축(카테고리)으로 오염이 번진다. 게이트 2의 카테고리 횡단 비율이 이걸 감시한다.
3. **중복 태그** — 위 다양성 규칙으로 완화하되, "인접 개념이지만 서로 다른 약점"과 "같은 개념의 다른 이름"을 그래프만으로는 구분할 수 없다.
4. **LATENT의 자기 확신** — 안 푼 태그를 취약하다고 판정해 그 주제 문항을 생성하고, 그 결과가 다시 프로필에 들어간다. `docs/RECOMMENDATION.md` 리스크 4(추천 루프의 자기 참조)가 한 단계 더 증폭된 형태다. 요청당 LATENT 1개 상한이 유일한 완화책이다.
5. **리소스 낡음** — `docs/TAG.md` 사전을 고치면 `tag-neighbors.tsv`가 낡는다. 리소스 계약 테스트(모든 이름이 사전에 존재)로 잡는다.
6. **신규 레벨의 판정 잡음** — LLM이 `SOLID` / `SOLID_NARROW`를 흔들리게 구분하면 해상도가 아니라 잡음이 늘어난다. 게이트 4가 유일한 방어선이고, 미달 레벨은 넣지 않는다.

## **테스트 기준**

- **순수 단위테스트** (Spring 컨텍스트·LLM 없이) — `NeighborhoodSmoother`(빈 그래프면 raw 불변, conf 0 이웃 무시, 분모 0이면 카테고리 폴백, 이웃 약점도에 단조, **입력 맵을 섞어도 같은 결과**), `TagConfidence`(표본 0이면 0, **일 단위로만 감쇠**, [0,1] 클램프), `MasteryScore`(**밴드를 절대 넘지 않음**, `null`은 0이 아니라 "신호 없음"), `TagWeaknessClassifier`(STRUCTURAL·INCIDENTAL·LATENT 경계 ±ε 전수), `TagNeighborGraph.of`(자기엣지·비정렬·중복 거부), `MasteryLevel`(10레벨 전부 `parent()`가 기존 6분류로 매핑).
- **리소스 계약 테스트** — `tag-neighbors.tsv`의 모든 이름이 사전에 존재, K ≤ 상한, similarity ∈ (0,1], 자기엣지 없음. 사전 수정 후 리소스가 낡는 함정을 잡는다. `QuestionRepositoryTest.findQuestions_excludesGeneratedSource`(countQuery 함정)와 같은 급의 가드다.
- **통합** — 안 푼 태그에 LATENT 등장, 강한 이웃 속 오답 1건에 INCIDENTAL, **플래그 off면 오늘과 숫자가 완전히 동일**(`WeaknessProfileCalculatorTest`).
- **픽스처** — `TagNeighborGraphFixture`는 체이닝 빌더로 둔다(`graph().edge("인덱스", "복합 인덱스", 0.8).build()`). 기존 `QuestionFixture`·`TagFixture`·`SolvedMultipleChoiceFixture`·`EssaySolvedFixture`는 그대로 재사용한다.
- **Python** — 가짜 벡터를 주입해 `tools/question-pipeline/tests/test_pipeline.py`에 추가한다("LLM 호출 0회" 성질 유지).
- **손댈 기존 테스트** — `TagWeakness`에 필드를 추가하면 `RecommendationTopicPolicyTest`가 `new TagWeakness(...)` 직접 호출로 컴파일 실패한다. 기존 4인자 형태를 보존하는 `TagWeakness.observed(...)` 정적 팩토리를 함께 넣는다. `WeaknessProfileCalculatorTest`의 폴백 계약 테스트는 플래그 off로 green을 유지하고 플래그 on 형제 테스트를 추가한다. `RecommendationServiceTest.weakTags_returnsTopFourInWeaknessOrder`는 다양성 규칙이 순서를 바꾸므로 **단정을 느슨하게 하지 말고 의도적으로 갱신**한다.
