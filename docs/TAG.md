# 문제 태그 사전

> 문제 시드 생성 시 `question_tag.name`에 넣을 수 있는 **태그의 전체 목록**과 부여 규칙을 규정하는 문서다.
> `docs/SCRIPT.md`(객관식)와 `docs/SCRIPT_ESSAY.md`(서술형)가 공통으로 이 문서를 참조한다.
> 두 스크립트를 프롬프트로 사용할 때는 **이 문서를 반드시 함께 제공**한다.

---

## 0. 왜 사전이 필요한가

과거에는 문항을 만들면서 태그를 즉흥적으로 붙였다. 그 결과 `src/main/resources/data2.sql`(350문항)에는 **서로 다른 태그가 638개** 생겼고, 대부분 한 번만 등장하며 `시간복잡도`/`시간 복잡도`처럼 표기만 다른 중복도 섞였다.

백엔드에는 `Tag` 엔티티도, `question_tag`의 유니크 제약도 없다(`QuestionTag`는 `question_id` + `name` 문자열을 그대로 들고 있다). 즉 **DB가 걸러 주지 않으므로 생성 단계에서 사전으로 통제해야 한다.**

태그 사전은 **8개 카테고리** 전체를 덮는다(`DB` · `NETWORK` · `ALGORITHM` · `DATA_STRUCTURE` · `OS` · `DESIGN_PATTERN` · `LANGUAGE` · `GENERAL_CS`).

그래서 생성 순서를 뒤집는다.

```
(기존) 카테고리 선택 → 문항 생성하면서 태그도 즉석에서 부여
(현재) 카테고리 선택 → 태그 사전 확정 → 사전의 태그를 축으로 문항 생성
```

## 1. 태그 작성 기준

새 태그를 사전에 추가할 때 지키는 기준이다. (생성 시점에는 사전을 그대로 쓰고 새로 만들지 않는다 — §3 참고)

- **개념 단위 명사구**로 쓴다. 1~4 단어. 문장·서술·물음표 금지
  - 좋음: `트랜잭션 격리 수준`, `해시 충돌`, `가비지 컬렉션`
  - 나쁨: `트랜잭션은 왜 필요한가`, `인덱스를 타지 않는 경우에 대하여`
- **카테고리명 자체를 태그로 쓰지 않는다.** `NETWORK`, `DB` 같은 태그 금지 (`data.sql`에 남아 있는 안티패턴)
- **정답을 암시하는 표현을 넣지 않는다.** 태그는 문제은행 목록·필터에 노출되므로 태그만 보고 정답을 유추할 수 있으면 안 된다
- **한 카테고리 안에서 서로 겹치지 않게** 구성한다. 상위 개념과 그 하위 개념을 둘 다 태그로 두려면, 문항에서 명확히 구분해 쓸 수 있을 만큼 층위가 달라야 한다 (예: `인덱스` vs `커버링 인덱스`는 OK)
- **표기를 하나로 고정한다.** 띄어쓰기·영문 대소문자·조사 없이 사전에 적힌 문자열이 유일한 정답 표기다
- **태그 이름은 8개 카테고리를 통틀어 유일하다.** `question_tag.name`은 카테고리와 무관한 전역 문자열이므로, 두 카테고리에 걸치는 개념은 이름을 구분한다. 실제로 이렇게 갈라 둔 것들:
  - DB `트랜잭션 데드락` ↔ OS `데드락`
  - DB `트랜잭션 전파` ↔ GENERAL_CS `분산 트랜잭션과 사가`
  - OS `캐시와 지역성` ↔ GENERAL_CS `캐시 전략` · `분산 캐시`
  - NETWORK `토큰 인증` · `쿠키와 세션` ↔ GENERAL_CS `인증과 인가` · `JWT` · `OAuth 2.0`
- **카테고리당 개수는 고정하지 않는다.** 신입 개발자에게 중요한 개념이면 넣는다. 카테고리마다 다뤄야 할 범위가 다르므로 수를 억지로 맞추지 않는다. 대신 §3의 커버리지 규칙을 지킨다

## 3. 문항–태그 부여 규칙 (SCRIPT.md · SCRIPT_ESSAY.md 공통)

1. **사전에 없는 태그는 절대 만들지 않는다.** 표기 변형도 새 태그로 취급한다 (`시간복잡도` ✗ / `시간 복잡도` ✓, `HTTPS` ✗ / `HTTPS와 TLS` ✓)
2. 각 문항은 **주 태그(primary) 1개 필수 + 관련 태그 0~2개** → 문항당 태그 **1~3개**
3. **주 태그**는 그 문항이 측정하는 가장 핵심적인 개념 하나다. `question_tag` INSERT에서 **항상 첫 행**으로 쓴다
4. **관련 태그**는 그 문항이 실제로 함께 측정하는 개념일 때만 붙인다. "연관 있어 보인다"는 이유로 붙이지 않는다. 애매하면 주 태그 하나만 쓴다
5. 관련 태그도 **같은 카테고리 사전 안에서만** 고른다 (카테고리 교차 금지)
6. **회차 내 주 태그 중복 금지**: 한 회차(1회 생성분) 안에서 같은 태그를 두 문항의 주 태그로 쓰지 않는다. 문항 N개면 서로 다른 태그 N개가 주 태그로 배정된다
7. **카테고리 전체 커버리지**: 그 카테고리의 **모든 태그가 누적 생성분에서 최소 1회는 주 태그**로 등장해야 한다. 카테고리 태그 수가 1회 생성분보다 많으면 **회차를 나눠** 진행하고, 회차마다 **아직 주 태그로 쓰이지 않은 태그부터** 소비한다
   - 예: NETWORK 40개 태그를 객관식(1회 25문항)으로 덮으려면 2회차가 필요하다. 1회차 25개, 2회차 나머지 15개(+ 이미 쓴 태그 10개를 다시 주 태그로 써서 25문항을 채운다)
8. 관련 태그는 회차·문항을 넘나들며 겹쳐도 무방하다. 위 제약은 **주 태그에만** 적용된다

## 4. 사전 확장·수정

- 사전을 늘리거나 표기를 바꾸는 것은 **이 문서를 고치는 것으로만** 한다. 생성 중에 임의로 하지 않는다
- 태그를 바꾸면 이미 들어간 시드(`src/main/resources/data2.sql`)의 태그와 어긋난다. 소급 정리 여부는 별도로 판단한다
- 태그를 추가할 때는 **8개 카테고리 전체를 통틀어 이름이 겹치지 않는지** 반드시 확인한다(§1). 확장하면서 가장 깨지기 쉬운 규칙이다
- 객관식 1회 생성분은 `docs/SCRIPT.md`의 "5개 클러스터 × 5개 태그 = 25문항" 구조상 항상 25문항이다. 카테고리 태그 수가 25의 배수가 아니어도 무방하며, 마지막 회차에서 이미 쓴 태그를 주 태그로 재사용해 25문항을 채운다
