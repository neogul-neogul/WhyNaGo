# 도메인 문서

> 이 문서는 프런트엔드 **문제 풀이 화면**(`front` 의 `MultipleChoiceQuiz` / `EssayQuiz` / `ProblemBank` / `mocks/questions.ts`)과 **학습 기록·진척도·주간 리포트 화면**(`front` 의 `RecordsPage` / `ProgressPage` / `WeeklyPage`, `mocks/records.ts` / `mocks/progress.ts`)에서 관찰되는 동작을 도메인 모델로 정리한 것이다.

## 엔티티

### Question (문제)

문제은행에 노출되는 문제를 표현하는 엔티티다. **객관식은 본질문·꼬리질문이라는 엔티티 차원의 구분이 없다** — `type = MULTIPLE_CHOICE`인 `Question`은 전부 그 자체로 완결된 독립적인 문제이며, 예외 없이 문제은행 목록에 노출·검색·직접 선택이 가능하다.

- **객관식**: "본 질문"·"꼬리질문"이라는 말은 한 풀이 세션 안에서 문항이 등장하는 순서를 가리키는 표현일 뿐이다. 어떤 `Question`의 선택지(`AnswerChoice.relatedQuestionId`)가 다른 `Question`을 가리키면 그 대상이 이어서 등장하는 "꼬리질문" 역할을 하지만, 그 대상 역시 다른 문항과 동등한 독립 `Question`이므로 문제은행에서 사용자가 직접 골라 그 자체로 풀 수도 있다. 별도 테이블이 아니라 같은 `Question`/`AnswerChoice` 테이블로만 표현한다. → [객관식 꼬리질문 분기·진행 정책](#꼬리질문-분기꼬리-진행-정책) 참고.
- **서술형**: 본 질문만 이 엔티티로 저장한다(`type = ESSAY`). 꼬리질문은 세션마다 AI가 동적으로 생성하므로 이 엔티티로 저장하지 않는다 — 객관식과 달리 서술형은 본질문/꼬리질문의 저장 방식 자체가 다르다(꼬리질문이 처음부터 `Question`으로 남지 않음). → [서술형 꼬리질문 생성 정책](#서술형-꼬리질문-생성-정책) 참고.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 문제 ID | PK |
| title | 제목 | 문제은행 목록에 노출되는 짧은 제목 (예: "TCP와 UDP의 핵심 차이") |
| content | 지문 | 실제 문제 본문/발문 |
| type | 유형 | `MULTIPLE_CHOICE`(객관식) \| `ESSAY`(서술형) |
| difficulty | 난이도 | `LOW`(하) \| `MEDIUM`(중) \| `HIGH`(상) |
| category | 카테고리 | `DB` \| `NETWORK` \| `ALGORITHM` \| `DATA_STRUCTURE` \| `OS` \| `DESIGN_PATTERN` \| `LANGUAGE` \| `GENERAL_CS` |
| explanation | 정답 해설 | 문제 전체(정답) 해설. 채점 후 항상 노출. 선택지별 오답 사유(`AnswerChoice.explanation`)와 별개 |
| rubric | 채점 기준(루브릭) | 서술형 채점 기준. `{criteria: [{point, weight}], followupScope: {allowed, forbidden}}` JSON 한 컬럼. 항목 3~5개·배점 합 10. 출처는 `tools/question-pipeline`이며 **백필 전에는 `null`**이다 → [서술형 정답 판정 정책](#서술형-정답-판정-정책) |

> **집계(파생) 값** — 문제은행 화면의 `완료한 사람 수`, `정답률`, 사용자별 `상태(완료/오답/안 푼 문제)` 는 `SolvedMultipleChoice` 를 집계해 얻는 조회용 값이며 `Question` 컬럼으로 저장하지 않는다. → [문제은행 표시 정책](#문제은행-표시-정책)

### Tag (태그 사전)

태그 사전 그 자체다. 원본은 `docs/TAG.md`이며 시드(`data-tag.sql`)로 적재한다. 런타임에 태그를 새로 만드는 경로는 없다(사전 확장은 별도 작업).

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 태그 ID | PK |
| name | 태그명 | 카테고리를 통틀어 유일 |
| category | 카테고리 | 그 태그가 속한 카테고리 |

문항이 하나도 없는 태그도 행으로 존재한다. 그래서 맞춤 문제 생성 시 후보 태그를 "문항이 있는 태그"가 아니라 사전 전체에서 고를 수 있다.

### QuestionTag (문제–태그 연결)

프런트의 `keywords`(예: "TCP/UDP", "전송 계층")에 대응한다. 한 문제에 여러 태그.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 연결 ID | PK |
| questionId | 문제 ID | FK → Question |
| tagId | 태그 ID | FK → Tag |

태그 이름을 이 테이블에 직접 두지 않는다(반정규화 제거). 사용자별 숙련도를 **태그 단위로 붙일 대상(`tagId`)**이 필요했기 때문이다. 부여 순서를 유지하며, 첫 행이 그 문항의 주 태그다.

### MasteryRecord (숙련도 판정 이력)

문제를 풀 때마다 남는 판정 1건이다. 한 번의 채점이 그 문항의 태그 개수만큼 행을 만든다.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 판정 ID | PK |
| userId | 사용자 ID | FK → User |
| questionId | 문제 ID | FK → Question |
| tagId | 태그 ID | FK → Tag. 태그가 없는 문항이면 null |
| category | 카테고리 | 항상 채운다 |
| level | 숙련도 | `MasteryLevel` 6분류 |
| reason | 판정 근거 | AI 판정(`AI_ESSAY`)이면 답변에서 근거를 짚은 문장, 규칙 판정(`RULE_CHOICE`)이면 정답 여부·평균 대비 소요시간을 옮긴 문장 |
| source | 판정 출처 | `AI_ESSAY`(서술형 채점 시점) · `RULE_CHOICE`(객관식 세션 저장 시점) |
| createdAt | 판정 시각 | |

### UserTagMastery (태그별 현재 숙련도)

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | ID | PK |
| userId | 사용자 ID | FK → User |
| tagId | 태그 ID | FK → Tag |
| level | 현재 숙련도 | 새 판정이 오면 덮어쓴다 |
| reason | 근거 | 가장 최근 판정의 근거 |
| updatedAt | 갱신 시각 | |

`(userId, tagId)` 조합당 1행이다. 숙련도는 "지금 이 주제를 얼마나 아는가"이므로 과거 판정을 평균하지 않고 덮어쓴다. 되짚어야 할 때는 `MasteryRecord` 이력을 본다.

### AnswerChoice (객관식 선택지)

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 선택지 ID | PK |
| questionId | 문제 ID | FK → Question (이 선택지가 속한 문제) |
| content | 내용 | 보기 텍스트 |
| sequence | 보기 순서 | 1부터. 화면의 보기 번호(1·2·3·4) |
| isCorrect | 정답 여부 | 이 보기가 정답인지. 한 문제에 `true` 는 정확히 1개(단일 정답) |
| explanation | 오답 해설 | 이 보기를 골랐을 때의 "왜 틀렸나" 해설. **정답 보기는 비움** |
| relatedQuestionId | 연결 꼬리질문 ID | 이 보기 선택 후 채점 시 이어지는 꼬리 `Question`. 없으면(null) 그 보기 선택 시 세션 종료 |

### SolvedSession (풀이 세션)

본 질문부터 꼬리 질문까지, 한 번에 이어 푼 하나의 풀이 단위.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | 세션 ID | PK |
| userId | 사용자 ID | FK → User |
| type | 유형 | `MULTIPLE_CHOICE` \| `ESSAY` |
| status | 상태 | `COMPLETED`(끝까지 진행). 저장 API는 완료된 세션만 받는다 — [세션 종료 정책](#세션-집계-정책) |
| totalCount | 전체 문항 수 | 세션에서 실제 응답한 문항 수(본질문+거친 꼬리질문) |
| correctCount | 정답 수 | 맞힌 문항 수 |
| startedAt | 시작 시각 | 학습 기록의 소요시간(`time`)을 `solvedAt - startedAt`으로 도출하는 데 필요 → [학습 기록 집계 정책](#학습-기록-집계-정책) |
| solvedAt | 완료 시각 | |
| createdAt | 저장 시각 | 세션 저장(레코드 생성) 시각. 조회 API 응답에는 노출하지 않는다 |

### SolvedMultipleChoice (푼 객관식 문항)

한 풀이 세션 안에서 사용자가 응답한 개별 객관식 문항(본질문/꼬리질문 각각 1행).

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | PK | |
| solvedSessionId | 풀이 세션 ID | FK → SolvedSession |
| userId | 사용자 ID | (조회 편의를 위한 비정규화, 세션에서도 도출 가능) |
| type | 문항 유형 | `MAIN`(본질문) \| `FOLLOWUP`(꼬리질문) |
| sequence | 세션 내 순서 | 본질문이면 1, 이후 꼬리질문 2·3… |
| userChoiceId | 유저 답안 | FK → AnswerChoice (사용자가 고른 보기) |
| answerChoiceId | 실제 답안 | FK → AnswerChoice (정답 보기). 정답은 불변이므로 `AnswerChoice.isCorrect` 로 도출 가능 — 조회 편의를 위한 선택 필드 |
| isCorrect | 정답 여부 | `userChoiceId == answerChoiceId` |
| solvedAt | 응답 시각 | 개별 문항 채점 시각 (선택). **세션 저장 시각이 모든 문항에 동일하게 들어가므로 문항 간 시간차를 나타내지 않는다** |
| elapsedSeconds | 소요 시간 | 그 문항을 푸는 데 걸린 초. 클라이언트가 측정해 세션 저장 요청에 담는다. 10분을 넘으면 600초로 잘라 저장하고, 0초 이하와 수집 전에 쌓인 기록은 `null`이라 집계에서 빠진다(`common.domain.ElapsedSecondsPolicy` — 서술형 채점도 같은 규칙을 쓴다) → [문제 통계 집계 정책](#문제-통계-집계-정책) |

### WrongNote (오답노트)

오답이 발생하면 자동 생성된다. — 단순히 "틀린 문제 목록"이며, 북마크 여부만 관리한다. **상태·반복 횟수·출처는 컬럼으로 두지 않는다.** → [오답 자동 저장 정책](#오답-자동-저장-정책)

| 이름              | 한글       | 설명                               |
|-----------------|----------|----------------------------------|
| id              | PK       |                                  |
| userId          | 사용자 ID   | FK → User                        |
| solvedSessionId | 풀이 세션 ID | FK → SolvedSession (틀린 문제 풀이 세션) |
| isBookmarked    | 북마크 여부   |                                  |

### EssaySolved (푼 서술형 문항)

한 풀이 세션 안에서 사용자가 응답한 개별 서술형 문항(본질문/꼬리질문 각각 1행). 꼬리질문은 AI가 세션마다 생성해 재사용 가능한 `Question` 이 없으므로, 발문·모범답안까지 이 행에 스냅샷으로 남긴다. → [서술형 풀이 흐름 정책](#서술형-풀이-흐름-정책)

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | PK | |
| solvedSessionId | 풀이 세션 ID | FK → SolvedSession |
| userId | 사용자 ID | (조회 편의를 위한 비정규화, 세션에서도 도출 가능) |
| type | 문항 유형 | `MAIN`(본질문) \| `FOLLOWUP`(꼬리질문) |
| sequence | 세션 내 순서 | 본질문이면 1, 이후 꼬리질문 2·3 |
| questionId | 본 질문 ID | FK → Question. 본질문(`MAIN`)만 값이 있고, 꼬리질문(`FOLLOWUP`)은 AI 생성이라 `null` |
| questionText | 질문 스냅샷 | 실제 발문. 꼬리질문은 원본 `Question` 이 없어 필수 저장, 본질문도 문구 변경 대비 스냅샷 |
| userAnswer | 내 답변 | 사용자가 작성한 서술형 답변 |
| feedback | AI 피드백 | LLM 채점 피드백 |
| modelAnswer | 모범답안 | 이 문항의 모범답안·해설 |
| isCorrect | 정답 여부 | LLM 채점 통과 여부. 세션 `correctCount` 집계에 사용 (판정 기준: [서술형 정답 판정 정책](#서술형-정답-판정-정책)) |
| solvedAt | 응답 시각 | 개별 문항 채점 시각 (선택) |

### DailyInterview (1일 1면접)

하루에 한 번 진행하는 면접 세션의 **진행 메타**다. 문답·피드백·모범답안·통과 여부는 **담지 않는다** — 그 단일 소스는 `EssaySolved`이며, 여기서는 `solvedSessionId`로 참조만 한다. → [1일 1면접 정책](#1일-1면접-정책)

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | PK | |
| userId | 사용자 ID | FK → User |
| interviewDate | 면접 날짜 | KST 기준 날짜. `(userId, interviewDate)` 유니크 — 하루 1회 제약의 근거 |
| category | 카테고리 | 그날 질문의 `Question.category` 스냅샷(결과 조회 편의) |
| questionId | 본 질문 ID | FK → Question. 그날의 면접 질문 |
| conversationId | 대화 식별자 | AI 대화 이력(ChatMemory) 키. 서버가 발급·보관하며 클라이언트에 노출하지 않는다 |
| status | 상태 | `IN_PROGRESS` \| `COMPLETED`. 취소된 면접은 상태가 아니라 **행 삭제**로 표현한다 |
| solvedSessionId | 풀이 세션 ID | FK → SolvedSession. 완료 시점에 채워진다. 미완료면 `null` |
| focusLossCount | 이탈 횟수 | 면접 중 화면을 벗어난 횟수. 클라이언트가 완료 시 보고한다(서버 강제 아님) |
| startedAt | 시작 시각 | 서버가 소유한다. 소요시간·타이머의 기준 |
| completedAt | 완료 시각 | 미완료면 `null` |
| createdAt | 생성 시각 | |

### DailyInterviewQuestion (오늘의 면접 질문)

그날의 면접 질문을 **전역으로 고정**하는 핀. 하루에 한 행만 존재하며, 그날 모든 사용자가 같은 질문을 받는다.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| interviewDate | 면접 날짜 | **PK**(`LocalDate`). 날짜 자체가 식별자다 |
| questionId | 질문 ID | FK → Question(`type = ESSAY`) |
| pinnedAt | 고정 시각 | 그날 처음 면접을 시작한 시점 |

### NotificationSetting (알림 설정)

사용자별 알림 수신 여부를 저장한다. 사용자당 1행이며, 가입 시 미리 만들지 않고 **최초 조회·수정 시점에 기본값으로 생성**한다(get-or-create).

`everyDayRemind = true`인 사용자에게는 `notification.scheduler.StudyReminderScheduler`가 매일 오후 9시(KST)에 학습 리마인드 메일을 발송한다(`notification.service.StudyReminderService`). 메일에는 "오늘 문제 풀이"(오늘자 `SolvedSession` 존재 여부 = 스트릭 유지 여부)와 "1일 1면접" 두 항목의 완료 여부가 담긴다. **1일 1면접은 아직 별도로 추적하는 도메인/컬럼이 없어 항상 "미완료"로 고정 표시**한다 — 실제 면접 기능이 생기면 `StudyReminderService`에서 이 값만 교체하면 된다. 메일 발송은 `common.mail.EmailSender`(특정 도메인에 종속되지 않는 공용 메일 발송 컴포넌트, 텍스트/HTML 모두 지원)를 이용하며, 이 기능이 첫 실사용처다. 발송 로직은 HTTP API로 노출하지 않는다 — 실제 메일 발송을 눈으로 확인하려면 `@Disabled` 처리된 `notification.service.StudyReminderManualSendTest`에 수신 이메일을 채우고 수동으로 실행한다.

| 이름 | 한글 | 설명 |
| --- | --- | --- |
| id | | PK |
| userId | | FK → User (unique, 사용자당 1행) |
| everyDayRemind | 매일 학습 리마인드 | 학습 기록이 없으면 알림. 기본값 true |

### ProblemSet (문제집)

사용자가 원하는 문제를 모아 만드는 이름 붙은 목록. 유튜브의 "재생목록"과 같은 개념이다. **항상 본인만 볼 수 있다** — 공개 범위(visibility) 같은 필드 자체가 없다. 공유·탐색 기능이 없고 앞으로도 개인 전용 리소스라는 전제이므로, 안 쓰는 필드를 미리 만들어 두지 않는다.

## 정책 · 제약

### 객관식 응답 규칙
- 선택지는 **단일 선택**이다. 한 문제의 `AnswerChoice.isCorrect == true` 는 **정확히 1개**(단일 정답).
- 채점("정답 확인")은 선택지가 선택된 상태에서만 가능하다.
- **한 문항당 1회만 응답**한다. 채점 후에는 선택을 바꿀 수 없다.
- 채점 즉시 정답 해설(`Question.explanation`)을 노출한다. 오답이면 사용자가 고른 보기의 오답 해설(`AnswerChoice.explanation`)을 함께 노출한다.
- 선택지는 **4개 고정**(4지선다).

### 꼬리질문 분기·꼬리 진행 정책
- 꼬리질문은 **사용자가 고른 보기(`AnswerChoice`)의 `relatedQuestionId`** 로 이어진다(보기별 분기).
- 공개 시점: **직전 문항을 채점하면** 이어질 꼬리질문이 공개된다. **정답/오답과 무관**하다.
- 고른 보기의 `relatedQuestionId` 가 없으면 그 지점에서 세션이 종료된다.
- **깊이 상한**: 한 세션은 **최대 3문항(본질문 + 꼬리질문 2개)**까지만 진행한다. `relatedQuestionId`가 있어도 3문항째에 도달하면 더 진행하지 않고 그 지점에서 세션을 종료한다(서술형과 동일한 깊이). 물론 그 전에 `relatedQuestionId`가 없어 자연 종료될 수도 있다.
- `relatedQuestionId`가 가리키는 대상은 별도 하위 타입이 아니라 **그 자체로 독립된 `Question`**이다. 어떤 세션에서 꼬리질문으로 등장한 문항이, 문제은행에서는 사용자가 직접 골라 풀 수 있는 본 문제이기도 하다. → [문제은행 표시 정책](#문제은행-표시-정책) 참고.
- 현재 `MultipleChoiceQuiz`는 이 정책대로 구현되어 있다: 채점 응답(`ChoiceGradingResponse.nextQuestion`, 즉 선택한 보기의 `relatedQuestionId`가 가리키는 문항)을 다음 문항으로 사용하되, 3문항에 도달하면 `nextQuestion`이 있어도 무시하고 세션을 종료한다.

### 서술형 풀이 흐름 정책
- 서술형은 본 질문부터 꼬리질문2까지 이어 푸는 하나의 `SolvedSession`(`type = ESSAY`)이다.
  1. **본 질문 조회**: DB의 `Question`(`type = ESSAY`)을 제시한다.
  2. **답변·채점 반복**: 답변1 → 꼬리질문1 → 답변2 → 꼬리질문2 → 답변3 순으로, 답변을 제출하면 즉시 채점하고 그 뒤에 다음 꼬리질문을 생성한다.
  3. **세션 저장**: 전체 스레드를 `SolvedSession` 1건 + `EssaySolved` 3행으로 저장한다.
- 채점 결과(피드백·모범답안·정답 여부)는 각 문항의 `EssaySolved` 에 담긴다.
- 꼬리질문 깊이·생성 맥락은 → [서술형 꼬리질문 생성 정책](#서술형-꼬리질문-생성-정책), 저장·집계 규칙은 → [세션 집계 정책](#세션-집계-정책) 참고.
- ⚠️ **프런트 정합 필요**: 현재 `EssayQuiz` 는 꼬리질문·피드백·모범답안을 mock 에 미리 정의해 순차 노출한다. 실제 서버는 답변마다 LLM 채점 후 꼬리질문을 동적 생성하므로 연동 시 수정이 필요하다.

### 서술형 꼬리질문 생성 정책
- 객관식과 달리 꼬리질문을 **미리 만들어 두지 않는다**. 풀이 세션마다 AI가 **동적으로 생성**하므로 재사용 가능한 `Question` 이 아니며, 그 세션의 `EssaySolved` 스냅샷에만 남는다.
- **깊이 고정**: 본 질문 + 꼬리질문 2개 = **총 3문항**이다. 꼬리질문2까지 답하면 세션이 종료된다.
- **생성 입력(누적 맥락)**: 각 꼬리질문은 직전까지의 전체 문답을 입력으로 생성한다.
  - 꼬리질문1 = `본 질문 + 답변1`
  - 꼬리질문2 = `본 질문 + 답변1 + 꼬리질문1 + 답변2`
- **채점과 순서**: 답변을 제출하면 LLM이 그 답변을 채점(피드백·모범답안 반환)하고, 이어서 다음 꼬리질문을 생성한다. 채점 결과(정답/오답)와 무관하게 꼬리질문2까지 진행한다.
- **대화 세션 유지**: 누적 맥락을 매 요청에 다시 싣지 않고, 서버가 대화 이력(ChatMemory)을 `conversationId` 단위로 보관해 주입한다. 클라이언트는 이번 턴의 질문·답변만 보낸다. 진행 단계(꼬리질문 생성 여부)는 서버가 대화 이력의 턴 수로 판단하며, 3문항이 끝나면 대화 이력을 정리한다.
- 전체 풀이 흐름과 저장 시점은 → [서술형 풀이 흐름 정책](#서술형-풀이-흐름-정책) 참고.

### 서술형 정답 판정 정책
- 점수(`score`)는 **0~10 정수**이고 산출 경로가 두 갈래다.
  - **문항에 루브릭이 있고 본 질문 턴이면**: 채점 AI가 루브릭 항목마다 충족 여부(`met`)를 판정하고, 서버가 **충족한 항목의 배점 합**을 점수로 계산한다. 루브릭 배점 합이 항상 10이므로 그대로 0~10이 된다. AI가 응답에 적은 점수는 쓰지 않는다 — 점수와 항목 판정이 어긋나는 것을 구조적으로 막는다.
  - **루브릭이 없거나 꼬리질문 턴이면**: 기존대로 LLM이 매긴 점수를 그대로 쓴다. 꼬리질문은 세션마다 AI가 만들어 참조할 `Question`이 없고 따라서 루브릭도 없다.
- 두 경로 중 어느 쪽이든 그 위에 **소요시간 가감**을 얹고 0~10으로 자른다. → [서술형 소요시간 반영 정책](#서술형-소요시간-반영-정책)
- 서버가 **임계값 7**로 통과 여부를 산출한다: `score >= 7` 이면 통과(`EssaySolved.isCorrect = true`), 미만이면 미통과. 시간 가감이 이 경계를 넘길 수 있다.
- 판정 정책(임계값)은 **서버/도메인이 소유**한다. 점수 자체는 저장하지 않고 통과 여부(`isCorrect`)만 남긴다.
- `isCorrect`는 채점 API 응답으로 반환되며, 완료 세션 저장 시 클라이언트가 그대로 전달해 세션 `correctCount` 집계에 쓰인다.
- 임계값 튜닝·다단계 등급 등 고도화는 추후 과제다.

### 서술형 루브릭 채점 정책
- 루브릭은 `Question.rubric`에 저장된 채점 기준이다. 항목(`point`)마다 배점(`weight`)이 있고 합은 정확히 10이며, 꼬리질문 가드레일(`followupScope`)을 함께 갖는다. 만드는 곳은 `tools/question-pipeline`이고 앱은 읽기만 한다.
- **적용 범위는 본 질문 턴 하나**다. 판별은 대화 이력의 완료 턴 수로 하고(0턴이면 본 질문), 꼬리질문 턴에는 루브릭을 프롬프트에 내려보내지 않는다.
- 채점 응답에는 항목별 **충족 여부와 그 근거**가 함께 실린다(`grading.rubricCriteria`). 사용자가 왜 그 점수인지, 어떤 기준을 놓쳤는지 항목 단위로 볼 수 있게 하는 것이 목적이다. 루브릭이 없는 턴에는 **빈 배열**이며 `null`로 내려가지 않는다.
- 프롬프트에는 루브릭이 없어도 `criteriaResults`를 빈 배열로 두라고 명시한다. 대화 이력에 본 질문 턴의 루브릭이 남아 있어, 지시하지 않으면 꼬리질문 턴에도 항목 판정을 만들어낸다.
- **AI 응답이 루브릭과 맞지 않으면 채점을 실패시키지 않는다.** 판정 개수가 항목 수와 다르거나 항목 번호가 범위를 벗어나거나 중복되면, 항목 판정을 버리고 LLM 점수로 폴백하고 경고 로그만 남긴다(숙련도를 못 받았을 때 채점은 그대로 응답하는 것과 같은 태도).
- `followupScope`는 꼬리질문 생성 지시에 함께 내려 "한 단계 더 들어가도 되는 개념"과 "넘어가지 말 영역"의 범위로 쓴다.
- **루브릭 백필 전에는 모든 문항의 `rubric`이 `null`이고 채점은 루브릭 도입 이전과 똑같이 동작한다.**

### 서술형 소요시간 반영 정책
- 서술형 채점 API는 문항별 소요시간(`elapsedSeconds`)을 함께 받아 **프롬프트와 점수 양쪽에** 반영한다. 답변 내용만 보면 "정확하지만 한참 헤맨 답변"과 "즉시 정확히 쓴 답변"을 구분할 수 없다. 객관식은 이미 정답 여부 × 평균 대비 소요시간으로 판정하고 있어(→ [숙련도 판정 정책](#숙련도-판정-정책)) 두 트랙의 신호가 어긋나 있었다.
- **절대 초가 아니라 그 문항의 평균 대비 비율**로 해석한다. 같은 90초가 쉬운 문항에서는 느리고 어려운 문항에서는 빠르다. 기준선은 `QuestionStat.avgElapsedSeconds`이며, 통계가 없거나 표본이 5건 미만이면 기본값 180초를 쓴다.
- 빠름·보통·느림의 눈금(`FAST` 0.7 미만 / `SLOW` 1.5 초과)은 **객관식 숙련도 판정과 공유**한다(`common.domain.ElapsedPacePolicy`). 두 트랙이 다른 임계값을 쓰면 같은 소요시간이 학습 기록과 채점 결과에서 다르게 해석된다.
- **점수 가감은 서버가 결정적으로 한다**: `FAST` `+1`, `SLOW` `-1`, `NORMAL` `0`. 루브릭 배점 합(또는 LLM 점수)에 얹고 0~10으로 자른다. 가감폭을 루브릭 항목 배점(3~4점)보다 작게 둔 이유는 시간이 내용 판정을 뒤집지 못하게 하는 것이다.
- **AI는 점수를 시간으로 조정하지 않는다.** 프롬프트에 시간을 주면서 "score는 시간으로 조정하지 마라"고 명시한다. 모델이 함께 반영하면 같은 신호가 두 번 먹는다. AI 쪽에서 시간은 `mastery` 판정과 `feedback`에만 쓴다.
- 클라이언트가 보고하는 값이라 신뢰하지 않는다. 저장 경로와 **같은 정규화**(`common.domain.ElapsedSecondsPolicy`: 상한 600초, 0 이하는 미측정)를 거친다. 두 경로가 다른 상한을 쓰면 채점에 반영된 시간과 기록에 남는 시간이 어긋난다.
- **미측정이면 시간을 아예 쓰지 않는다.** 프롬프트에 "측정되지 않았다"고 알려 내용만으로 판정하게 하고, 점수도 조정하지 않으며 응답의 `grading.solvingTime`은 `null`이다.
- 반영 결과는 채점 응답에 그대로 실린다(`grading.solvingTime`). 이게 없으면 루브릭 항목 배점 합과 `score`가 어긋나 보여 버그처럼 읽힌다.
- 클라이언트는 같은 소요시간을 **두 번** 보낸다: 채점 요청(그 턴의 점수에 쓰려고)과 세션 저장 요청(기록에 남기려고). 채점 API는 아무것도 저장하지 않으므로(→ [서술형 풀이 흐름 정책](#서술형-풀이-흐름-정책)) 저장 시점에 다시 받아야 한다.
- 면접은 문항당 제한 시간이 180초라 실제 소요시간이 그 안에서만 나온다. 따라서 평균이 120초 미만인 문항에서만 `SLOW`가 나올 수 있고, 나머지는 `FAST`·`NORMAL`뿐이다. 별도 규칙을 두지 않고 같은 정책을 쓴다.

### 숙련도 판정 정책
- 숙련도 분류는 하나(`MasteryLevel` 6분류)이고 **판정 주체는 두 트랙**이다.
  - **서술형**: 채점 AI가 판정하고, 판정 근거(`masteryReason`)를 반드시 함께 반환한다(`EssayPromptV6`). 1차 근거는 답변 **내용**이고 평균 대비 소요시간을 보조 근거로 얹는다 — 정확하지만 뚜렷하게 오래 걸리면 `MASTERED`로 올리지 않는다. → [서술형 소요시간 반영 정책](#서술형-소요시간-반영-정책)
  - **객관식**: AI를 호출하지 않고 정답 여부 × 소요시간 비율로 서버가 판정한다(`MasteryPolicy`). 비율의 눈금은 서술형 채점과 공유한다(`common.domain.ElapsedPacePolicy`).
- 기록 시점은 **채점 응답을 내리는 시점**이다. 클라이언트가 채점 결과를 되돌려주는 저장 경로에 맡기면 값이 조작될 수 있고, 세션을 중도 이탈한 답변의 판정이 남지 않는다. 그래서 서술형 채점 API는 인증이 필요하다.
- 판정은 그 문항의 **모든 태그와 카테고리에 연결**해 기록한다. 태그가 없는 문항은 카테고리 신호로만 남는다.
- **꼬리질문 턴은 `AI_ESSAY_FOLLOWUP`으로 기록하되 태그별 현재값은 갱신하지 않는다.** 태그·카테고리는 루트 문항에서 가져온다. 현재값을 덮어쓰면 가장 깊은 프로브 판정이 그 태그의 숙련도가 되어 본질문을 제대로 답한 사용자가 불이익을 받는다. `mastery_record.turn`이 몇 번째 턴인지 남기며, `null`은 "본질문"이 아니라 "미지"다.
- AI가 숙련도를 빠뜨리면 채점은 그대로 응답하고 기록만 건너뛴다. 그 이력은 추천 집계에서 규칙 판정으로 폴백한다.
- 상세는 `docs/RECOMMENDATION.md` 숙련도 판정 정책을 따른다.

### 1일 1면접 정책

면접은 서술형 풀이와 **같은 3문항 흐름**(본 질문 + 꼬리질문 2개, AI 채점)을 쓰되, 하루 1회 제약과 진행 메타가 얹힌 형태다. → [서술형 풀이 흐름 정책](#서술형-풀이-흐름-정책)

- **하루 1회**: 한 사용자는 하루에 면접을 한 번만 볼 수 있다. `DailyInterview`의 `(userId, interviewDate)` 유니크 제약으로 강제하며, 시작 API를 두 번 호출하면 `INTERVIEW_ALREADY_STARTED_TODAY`다. 두 탭 동시 시작 같은 경합은 사전 조회로 막을 수 없으므로 DB 제약이 최종 방어선이다.
- **하루 경계는 KST(Asia/Seoul) 자정**이다. 스트릭의 "하루" 기준과 동일하다. → [학습 기록 집계 정책](#학습-기록-집계-정책)
- **날짜는 서버가 정한다**: 시작·조회 API 모두 날짜를 파라미터로 받지 않는다. 클라이언트가 날짜를 정하면 하루 1회 제약 자체를 우회할 수 있기 때문이다.
- **오늘의 질문은 전역 고정**: 그날 모든 사용자가 같은 질문을 받는다(`DailyInterviewQuestion`). 그날 **처음 면접을 시작한 사용자**의 요청에서 서술형(`ESSAY`) 문제 중 무작위로 하나를 뽑아 핀으로 저장하고, 이후에는 자정까지 그 핀을 읽는다. 서술형 문제가 하나도 없으면 `INTERVIEW_QUESTION_NOT_AVAILABLE`이다.
  - 트레이드오프(수용): 이미 면접을 본 사람이 오늘의 질문을 남에게 알려줄 수 있다. 서비스 성격상(경쟁이 아니라 학습 도구) 수용한다.
- **3문항 / 3분**: 본 질문 + 꼬리질문 2개, 제한 시간 180초. 시간 제한은 클라이언트가 표시·강제하며 **서버가 강제하지 않는다**.
- **이탈 감지**: 면접 중 화면을 벗어난 횟수를 클라이언트가 집계해 완료 시 `focusLossCount`로 보고한다. 서버는 값을 그대로 저장할 뿐 검증하지 않는다.
- **결과는 `SolvedSession`에 통합 저장한다**: 완료 시 `SolvedSession`(`type = ESSAY`) 1건 + `EssaySolved` 3행을 만든다. 서술형 풀이와 저장 구조가 완전히 같아서 학습 기록·오답노트에 자동으로 잡힌다. `DailyInterview`는 그 세션을 가리키는 포인터와 면접 고유 메타(이탈 횟수·면접 날짜)만 갖는다.
  - 트레이드오프(수용): 학습 기록에서 면접과 일반 서술형 풀이를 구분할 수 없다. 진입 경로 구분은 여전히 보류다. → [보류](#보류-추후-mvp)
- **진행 중 저장 없음**: 답변 채점 API는 아무것도 저장하지 않는다(서술형과 동일). 클라이언트가 3턴 결과를 들고 있다가 완료 시 한 번에 올린다. 따라서 **새로고침·브라우저 종료 시 오늘 면접을 잃는다**(진행 상태 복구는 범위 밖).
- **서버 사유 취소**: AI 장애·쿼터 초과로 **한 문항도 채점받지 못했으면** 면접을 취소해 오늘 자리를 돌려준다. `status = IN_PROGRESS`이고 채점 턴 수가 0일 때만 `DailyInterview` 행을 삭제하며, 그 외에는 `INTERVIEW_NOT_CANCELABLE`이다.
  - 채점 진행도는 클라이언트 주장이 아니라 **대화 이력의 턴 수**로 판정한다. "2문항 채점받고 마음에 안 들어 취소 후 재시작"하는 우회를 막는다.
  - 트레이드오프(수용): 대화 이력이 인메모리라 **서버가 재시작되면 턴 수가 0으로 리셋**되어 취소 창구가 다시 열린다.
- **`conversationId`는 서버가 소유한다**: 서술형 풀이는 클라이언트가 대화 식별자를 보관해 매 요청에 실어 보내지만, 면접은 `DailyInterview`에 저장해두고 서버가 꺼내 쓴다. 클라이언트는 `interviewId`만 보낸다. 취소 판정의 근거(턴 수)를 신뢰할 수 있는 이유다.

### 오답 자동 저장 정책
- 채점 결과가 오답이면 해당 문항이 **자동으로 오답노트에 저장**된다("오답노트에 자동 저장됨"). 한 세션에 오답이 하나라도 있으면 `WrongNote` 1건이 생성되며, 같은 세션에 대해 중복 생성되지 않는다(`userId`+`solvedSessionId` 유니크).
- **면접도 동일 정책이다**: 면접 완료로 만들어진 `SolvedSession`에 오답이 있으면 같은 방식으로 `WrongNote`가 생성된다. 오답노트에서 면접 오답과 일반 서술형 오답은 구분되지 않는다. → [1일 1면접 정책](#1일-1면접-정책)
- 사용자가 문제를 직접 삭제하거나 북마크할 수 있다.
- **상태·반복 횟수 없음**: 오답노트는 "미복습/복습 중" 같은 상태를 갖지 않는다. 목록 조회 필터는 **전체 / 북마크** 두 가지만 지원한다. 같은 문제를 반복해 틀렸는지는 별도로 집계하지 않는다(추후 필요해지면 `SolvedMultipleChoice`/`EssaySolved` 집계로 조회 시점에 계산하는 방식을 검토한다 — 컬럼으로 저장하지 않음).
- **출처(source) 미구현**: 오답노트가 문제 풀이 외의 경로(자가진단 오답, 재풀이, 직접 저장)에서도 생성될 수 있다는 아이디어는 있으나, 해당 기능들이 아직 없으므로 `WrongNote`에 출처 컬럼을 두지 않는다. 해당 기능이 실제로 추가될 때 함께 설계한다.

### 세션 집계 정책
- 본질문~꼬리질문 전체가 하나의 `SolvedSession` 이다.
- 결과 화면의 값 = 세션 집계: 정답률 `correctCount / totalCount`, 정답 수, 오답 수(`totalCount - correctCount`).
- 마지막 문항까지 답하고 "저장하기"로 끝낸 세션만 저장하며 상태는 `COMPLETED`다. 중간에 "종료하기"로 이탈한 풀이는 저장하지 않는다(중단 세션 저장은 추후 필요 시 별도 논의).

### 학습 기록 집계 정책
학습 기록(`/records`) 화면의 잔디·최근 기록, 진척도(`/progress`)의 스트릭·누적 통계, 주간 리포트(`/weekly`)는 별도 테이블 없이 `SolvedSession`(서술형 통합 시 `EssaySolved` 포함 — → [1일 1면접(서술형) 세션 통합](#보류-추후-mvp))을 **조회 시점에 집계**해 얻는 값이다. 오답노트가 상태·반복 횟수를 컬럼으로 두지 않고 집계로 계산하는 원칙(→ [오답 자동 저장 정책](#오답-자동-저장-정책))과 동일하게, 저장보다 집계를 우선한다.

- **최근 기록 항목** = `SolvedSession` 1건에 대응한다. `date`/`time`은 `solvedAt`·`startedAt`으로, `solved`/`correct`/`wrong`은 `totalCount`/`correctCount`/`totalCount - correctCount`로 도출한다. `cats`(카테고리 태그)는 세션에 포함된 문항들의 `Question.category`를 distinct 해 얻는다 — 서술형 꼬리질문(`EssaySolved.type = FOLLOWUP`)은 `questionId`가 없으므로 본질문 카테고리만 반영 가능하다.
- **연속 학습일(스트릭)·누적 학습일** = 사용자의 `SolvedSession.solvedAt` distinct 날짜 집합에서 계산하는 파생값이다. `LearningStats`/`ProgressMetric` 같은 별도 컬럼으로 저장하지 않는다.
- **잔디(일자별 학습량)** = 날짜별 `SolvedSession` 그룹핑 결과(세션 수·총 문항 수)를 시각화 등급(0~4단계)으로 변환한 값이다.

미확정 사항은 → [보류](#보류-추후-mvp) 참고. 구현된 조회 API는 → `docs/API.md` LearningRecord API 참고(최근 기록 목록·연속/누적 학습일·일자별 학습량). method(진입 경로) 구분과 잔디 등급·점수는 구현에서 제외했다.

### 점수·티어 산정 정책

진척도(`/progress`)의 점수·티어도 학습 기록과 같은 원칙을 따른다 — **별도 테이블 없이 `SolvedSession`·`SolvedMultipleChoice`·`EssaySolved`를 조회 시점에 집계**해 얻는다(→ [학습 기록 집계 정책](#학습-기록-집계-정책)). 유저별 누적값이라 `Question`에 담을 수 없고, 이미 저장된 풀이 이력과 `Question.difficulty`만으로 100% 재계산되는 파생값이기 때문이다.

여기서 말하는 "점수"는 잔디의 **"학습량 점수"(→ [보류](#보류-추후-mvp))와 다른 개념이다.** 잔디 점수는 하루 풀이량을 나타내는 시각화용 값이고, 이 점수는 문제를 맞혔는지에 따라 계정 전체에 누적되는 값이다.

**지급 조건** — 한 세션이 **본질문+꼬리질문을 전부 맞혔을 때만**(`correctCount == totalCount`) 그 세션의 문항이 점수 대상이 된다. 하나라도 틀리면 그 세션의 문항은 전부 0점이다. 세션의 문항 수는 유형에 따라 다르다(객관식은 보기의 `relatedQuestionId`에 따라 1~3문항, 서술형은 3문항 고정) — "3문항 전부"가 아니라 **"그 세션에 있는 문항 전부"**가 기준이다.

**배점 단위가 유형별로 다르다.**

| 유형 | 점수를 매기는 단위 | 하 | 중 | 상 |
| --- | --- | --- | --- | --- |
| 객관식 | 세션에 등장한 **문항 하나하나**(본질문·꼬리질문 각각) | 1점 | 2점 | 3점 |
| 서술형 | **본질문 하나**(꼬리질문 2개 포함해 총 3문항을 다 맞혀야 지급) | 4점 | 8점 | 12점 |

- 객관식 꼬리질문은 문제은행의 **독립된 `Question`**이므로(→ [꼬리질문 분기·꼬리 진행 정책](#꼬리질문-분기꼬리-진행-정책)) 자기 난이도로 따로 점수를 받는다. 본질문(중, 2점)에 꼬리질문(상, 3점)이 이어져 둘 다 맞히면 그 세션은 5점이다.
- 서술형 꼬리질문은 세션마다 AI가 생성해 참조할 `Question`도 난이도도 없으므로(→ [서술형 꼬리질문 생성 정책](#서술형-꼬리질문-생성-정책)) 본질문 난이도로만 매긴다. 1일 1면접도 저장 구조가 서술형과 같아 동일하게 계산된다.

**중복 지급 없음** — 같은 `Question`은 **최초로 정답을 낸 시점에 한 번만** 점수를 준다. 어떤 세션에서 꼬리질문으로 점수를 받은 문항은 나중에 다른 세션의 본질문으로 다시 나와도 점수가 오르지 않는다(역할이 아니라 `Question` 단위로 잠근다). 최초 성공 전에 실패한 시도는 점수 없이 지나갈 뿐이며, 이후 성공 기회를 막지 않는다.

**티어** — 누적 점수로 5단계를 판정한다. 구간 하한이 곧 진입 점수다.

| 티어 | 누적 점수 |
| --- | --- |
| 브론즈 | 0 ~ 57 |
| 실버 | 58 ~ 197 |
| 골드 | 198 ~ 419 |
| 플래티넘 | 420 ~ 676 |
| 다이아 | 677 ~ 700 |

- 상한 700은 티어 진행 바의 **표시 상한**으로 프로덕트가 정한 값이며, 실제 획득 가능한 최대 점수(문제은행에 있는 문항 수에 따라 달라짐)와는 별개다.
- 티어는 **총점** 기준이다. 카테고리별 점수에 이 구간을 대입하는 것은 의미가 없다(카테고리별 티어는 없다).

구현된 조회 API는 → `docs/API.md` Progress API 참고(점수·티어·카테고리별 점수/문항 수, 상단 통계).

### 문제은행 표시 정책
- 노출 대상: 조건(유형·난이도·카테고리·검색어)에 맞는 **모든** `Question`이 노출된다. 어떤 보기의 `relatedQuestionId`로 참조되는지 여부는 노출 여부에 영향을 주지 않는다 — 본질문/꼬리질문 구분으로 목록을 걸러내지 않는다.
- `완료한 사람 수` = 그 문제를 푼(세션에 포함된) 사용자 수(집계).
- `정답률` = 전체 사용자 응답 중 정답 비율(집계).
- 사용자별 `상태`: 해당 사용자가 그 문제를 마지막에 **맞혔으면 `완료`**, **틀렸으면 `오답`**, **푼 적 없으면 `안 푼 문제`**.
- 필터: 유형(전체/객관식/서술형), 난이도(전체/하/중/상), 카테고리, 제목·개념 검색.

### 문제집 추가·관리 정책

- 문제집에 문제를 담는 흐름은 **유튜브 재생목록에 영상을 추가하는 과정과 동일**하다. 문제 풀이 화면 상단 행(돌아가기와 정반대편)의 "문제집에 저장" 버튼을 누르면, 사용자가 만든 문제집을 체크박스 목록으로 보여주는 모달이 뜬다(모달 데이터는 `GET /api/problem-sets/membership?questionId=` — 각 문제집의 이름·문제 수와 함께 "이 문제가 이미 담겨 있는지"까지 한 번에 내려준다).
- 체크박스를 켜면 `PUT /api/problem-sets/{id}/items/{questionId}`로 즉시 추가되고, 끄면 `DELETE`로 즉시 제거된다. 둘 다 **멱등**이다 — 이미 담긴 문제를 다시 담으려 하거나 없는 문제를 빼려 해도 에러 없이 그냥 아무 일도 일어나지 않는다. 별도의 "저장" 확정 단계가 없다.
- 같은 모달에서 새 문제집을 만들 수 있다(이름만 입력, `POST /api/problem-sets`). **새로 만든 문제집에 지금 보고 있는 문제가 자동으로 담기지는 않는다** — 문제집은 항상 빈 상태로 생성되며, 방금 만든 문제집도 모달 목록에 다른 문제집과 동일하게 나타나므로 담으려면 그 항목을 다시 체크해야 한다.
- 담으려는 `questionId`가 실재하는 문제가 아니면(`PUT /api/problem-sets/{id}/items/{questionId}`) `QUESTION_NOT_FOUND`(문제 도메인의 기존 에러코드를 그대로 재사용, 문제집 도메인이 별도 에러코드를 만들지 않는다).
- **한 문제는 여러 문제집에 동시에 속할 수 있다** — 문제집끼리는 배타적이지 않다(폴더가 아니라 태그·재생목록에 가깝다).
- 문제집 상세 화면에는 **"상태"(완료/오답/안 푼 문제) 컬럼을 두지 않는다** — 임의 문제의 사용자별 풀이 상태를 계산하는 집계 로직이 아직 없다(문제은행 목록에도 없음 → [문제은행 표시 정책](#문제은행-표시-정책)). 없는 값을 지어내면 실제로 안 푼 문제를 "완료"로 잘못 보여줄 위험이 있어 제외했다.
- "제거"(`DELETE /api/problem-sets/{id}/items/{questionId}`)는 그 문제집에서만 문제를 빼며, 문제(`Question`) 자체나 다른 문제집에는 영향이 없다. "문제집 삭제"(`DELETE /api/problem-sets/{id}`)는 하위 `ProblemSetItem`을 모두 지우고 문제집 자체도 없앤다.
- 모든 조회·수정·삭제는 **본인 소유 문제집만** 가능하다(`ProblemSetReader.read`가 `findByIdAndUserId`로 검증, 없거나 본인 소유가 아니면 `PROBLEM_SET_NOT_FOUND`).

### 관리자 권한 정책

백오피스(관리자 기능)를 위해 `User`에 `role` 컬럼을 둔다. 값은 `USER`(일반 사용자) 또는 `ADMIN`(관리자)이며, 백오피스는 관리자 한 명이 쓰는 것을 전제로 한다.

- **가입으로는 관리자가 될 수 없다.** `User.create`·`User.createSocial`은 항상 `Role.USER`로 만든다. 관리자 전용 회원가입 경로도 없다.
- **승격은 운영 DB에서 직접 한다.** `UPDATE users SET role = 'ADMIN' WHERE email = ...`. 권한을 바꾸는 API도, `User`의 role 변경 메서드도 만들지 않는다 — 되돌리기 어려운 조작이고 관리자가 소수라, 코드에 경로 자체를 두지 않는 편이 안전하다. 관리자 계정은 일반 회원가입 API로 만든 뒤(비밀번호 해시·닉네임 검증을 정상적으로 태우기 위해) SQL로 승격한다.
- **로그인은 일반 사용자와 같은 엔드포인트를 쓴다.** 로그인 응답의 `role`을 보고 클라이언트가 관리자 화면으로 보낸다. → `docs/API.md` 권한
- **판정은 토큰으로 한다.** 권한은 JWT claim에 실려 `AdminInterceptor`가 `/api/admin/**`에서 확인한다(요청마다 조회하지 않는다). 권한이 없으면 `403 AUTH_FORBIDDEN`이다.
  - 단, **재발급 시에는 저장된 권한을 다시 읽어** 토큰에 담는다. 그러지 않으면 refresh token에 박힌 권한이 최대 7일간 이어져 승격·강등이 반영되지 않는다. 이 처리로 반영 지연은 access token 수명(30분) 이내다.
  - 트레이드오프(수용): 승격 후 최대 30분간 옛 토큰이 일반 사용자로 동작한다. 재로그인하면 즉시 반영된다.
- **관리자 계정도 `users` 테이블의 일반 행이다.** `nickname`·`position`·`dailyGoal`이 모두 NOT NULL이라 값이 채워지며, 관리자에게 의미 없는 값(예: `position`)이 로그인 응답에 함께 내려간다. 응답 스펙을 권한에 따라 나누지 않고 클라이언트가 무시하는 방식을 택했다 — 필드 두어 개를 아끼려고 같은 엔드포인트가 두 가지 스키마를 반환하게 만들지 않는다.
- **클라이언트의 권한 확인은 화면 표시용이다.** 실제 방어선은 서버의 403이며, 클라이언트가 권한을 조작해도 관리자 API는 열리지 않는다.

### 문제 통계 집계 정책

관리자가 보는 문제별 통계(전체 풀이 횟수·정답률·가장 많이 고른 선택지·보기별 선택 분포)는 별도 테이블이나 컬럼 없이 **`SolvedMultipleChoice`를 조회 시점에 집계**해 얻는 값이다. 오답노트가 반복 횟수를 저장하지 않고(→ [오답 자동 저장 정책](#오답-자동-저장-정책)), 학습 기록이 잔디·스트릭을 저장하지 않는 것과(→ [학습 기록 집계 정책](#학습-기록-집계-정책)) 같은 원칙이다.

- **유형별로 지표 집합이 다르다.** 객관식은 위 네 지표를 제공하고, 서술형은 선택지가 없어 분포·최다 선택지가 성립하지 않는다. 응답 스키마를 하나로 합치지 않고 유형별 엔드포인트로 나눈다. 서술형 통계는 아직 정하지 않았다(→ [보류](#보류-추후-mvp)).
- **본질문/꼬리질문을 구분하지 않는다.** 해당 `questionId`로 남은 모든 응답을 합산한다. 모든 `Question`이 동등한 독립 문항이고 등장 위치는 세션마다 다르므로(→ [결정 사항](#결정-사항-확정)), 나누면 한 문제의 정답률이 두 개가 된다.
- **정답률은 응답 시점에 저장된 `SolvedMultipleChoice.isCorrect`로 계산한다.** 단일 정답이라 "정답 보기의 선택 수 = 정답 수"가 성립하지만, 관리자가 문제를 수정해 보기를 교체하면 과거 응답과 어긋나므로 저장된 채점 결과를 쓴다.
- **분포는 현재 보기 목록을 기준으로 채운다.** 아무도 고르지 않은 보기도 0건으로 포함한다. 반대로 교체·삭제되어 현재 목록에 없는 보기를 고른 과거 응답은 분포에서 빠지되 전체 풀이 횟수에는 남는다 — 이때 분포 비율의 합은 100%에 못 미친다. 과거 풀이 횟수를 조용히 줄이지 않기 위한 선택이다.
- **문항별 소요 시간은 클라이언트가 측정해 보낸다.** 세션 저장 시 `solvedAt` 하나를 세션의 모든 문항에 동일하게 넣기 때문에 서버가 가진 값만으로는 문항 간 시간차를 낼 수 없다. 그래서 `SolvedMultipleChoice.elapsedSeconds`를 세션 저장 요청으로 받는다.
  - **구간은 "문항이 화면에 표시된 시점 ~ 정답 확인을 누른 시점"이다.** 채점 후 해설을 읽는 시간은 제외한다. 클라이언트마다 다른 구간을 재면 지표가 무의미해지므로 정의를 고정한다.
  - 서버가 직접 재지 않는 이유는 채점 API가 비인증·무상태 GET이고 객관식에는 진행 중 세션 개념이 없어, "문항을 언제 표시했는지"를 서버가 알 방법이 없기 때문이다. `startedAt`과 같은 신뢰 모델이다.
  - **수집 전에 쌓인 기록과 1시간을 넘는 이상치는 `null`이다.** 0으로 채우면 "0초에 풀었다"와 구분되지 않아 평균이 왜곡되고, `null`은 `avg()`가 알아서 제외한다. 이상치로 세션 저장 자체를 실패시키지는 않는다.
  - 평균 소요 시간 지표는 이 값이 쌓인 뒤에야 의미가 있으므로, 관리자 통계 응답은 표본 수를 함께 내려 몇 건 기준인지 드러낸다.

### 대시보드 지표 집계 정책

관리자 대시보드의 KPI·운영 알림도 [문제 통계 집계 정책](#문제-통계-집계-정책)과 같이 **집계 테이블 없이 조회 시점에 계산**한다. `SolvedSession`·`DailyInterview`·`users`가 원본으로 남아 있어 언제든 재계산할 수 있다.

- **날짜 경계는 `Asia/Seoul` 기준이다.** "오늘"은 KST 자정부터 하루의 끝까지이며, 학습 리마인더 배치(21시 KST)와 같은 기준이다. 서버 기본 시각대에 따라 지표가 흔들리지 않게 고정한다.
- **"풀이 수"는 세션 수가 아니라 문항 수(`SolvedSession.totalCount` 합)다.** 학습 기록의 일자별 문항 수와 같은 정의라(→ [학습 기록 집계 정책](#학습-기록-집계-정책)) 화면 간 숫자가 어긋나지 않는다. 면접 완료도 서술형 세션을 남기므로 면접 문항이 함께 잡힌다.
- **"활동 회원"은 해당 기간에 풀이한 회원이다.** 로그인·방문 로그가 없으므로 방문이 아니라 풀이가 기준이며, 같은 회원은 기간 안에서 한 번만 센다. 최근 7일은 오늘을 포함한 7일, 전주는 그 직전 7일로 두 구간이 겹치지 않는다.
- **면접 "참여"는 시작된 면접 수, "완료"는 `status = COMPLETED`인 면접 수다.** 하루에 한 명이 한 건만 가질 수 있으므로(→ [1일 1면접 정책](#1일-1면접-정책)) 참여 수는 곧 참여자 수다.
- **가입자 수는 `User.createdAt`이 있는 회원만 센다.** 이 컬럼은 가입 시각 추적을 시작할 때 nullable로 추가했다 — 운영 DB는 `ddl-auto: update`라 이미 행이 있는 테이블에 NOT NULL 컬럼을 넣을 수 없다. 추적 이전에 가입한 회원은 `null`로 남아 일자별 집계에서 빠진다. 전체 회원 수는 `createdAt`과 무관하게 전부 센다.
- **증감률·화살표 같은 표시 값은 서버가 만들지 않는다.** 비교가 필요한 지표는 현재·이전 두 숫자만 내려주고 문자열 조립은 클라이언트가 한다.
- **"1일1면접 미고정" 알림은 경고가 아니라 사실 전달이다.** 오늘의 문항은 배치가 아니라 첫 사용자가 면접을 시작할 때 고정되므로(→ [1일 1면접 정책](#1일-1면접-정책)), 아무도 시작하지 않은 이른 시각의 미고정은 정상 상태다. 서버가 기준 시각을 정해 경고로 격상하지 않고 미고정 사실만 알리며, 노출 여부·문구는 클라이언트가 판단한다.
- **AI 사용량(호출 수·추정 비용)과 메일 배치 알림은 아직 근거 데이터가 없다.** AI 호출 로그와 배치 실행 이력이 각각 생긴 뒤에 붙인다(→ [보류](#보류-추후-mvp)).

### 관리자 회원 지표 정책

관리자 회원 관리 화면이 쓰는 값도 조회 시점에 계산한다. 요약의 전체 회원 수·최근 7일 활동 회원 수는 [대시보드 지표 집계 정책](#대시보드-지표-집계-정책)과 **같은 집계 경로**를 쓰므로 두 화면의 숫자가 어긋날 수 없다.

- **목록 정렬은 회원 ID 내림차순(가입 역순) 하나뿐이다.** `createdAt`은 추적 이전 가입 회원이 `null`이라 정렬 키로 쓸 수 없다.
- **검색은 닉네임·이메일 부분 일치이며 대소문자를 구분하지 않는다.** 이메일은 관리자에게 마스킹하지 않은 원본을 내려준다 — 마스킹하면 문의 대응·검색에 쓸 수 없다. 표시용 마스킹은 클라이언트의 몫이다.
- **회원 상세의 "풀이 횟수"도 문항 수다.** 스트릭은 스트릭 조회와 같은 계산기를 쓰고, 면접 횟수는 `status = COMPLETED`만 센다.

**아직 서버가 제공하지 않는 값**은 다음과 같다. 화면은 컬럼을 유지하되 이 값들을 목업으로 채운다.

| 값 | 없는 이유 | 선행 조건 |
| --- | --- | --- |
| 점수 · 티어 | 풀이 이력에서 조회 시점에 파생되는 값이라(→ [점수·티어 산정 정책](#점수티어-산정-정책)) 컬럼이 없다. 목록 한 페이지를 계산하려면 회원마다 전체 세션·문항을 읽어야 하고, 서버가 티어로 정렬·필터할 수도 없다. | `users`에 점수 스냅샷 컬럼 도입. 점수·티어·필터·정렬을 한 번에 전환한다 |
| 최근 활동일 | 로그인·방문 로그가 없다. `max(SolvedSession.solvedAt)`으로 대체하면 컬럼 의미가 "방문"이 아니라 "학습"으로 바뀐다. | 방문/로그인 로그 도입, 또는 컬럼 라벨 변경 |
| 이상 징후 | "AI 과다"·"점수 불일치"를 판정할 AI 호출 로그와 기준이 없다. | AI 호출 로깅 + 판정 기준 정의 |
| 상태(활성/정지/탈퇴) | `User`에 상태 컬럼이 없고, 정지 시 로그인·API 차단과 탈퇴 흐름이 함께 필요하다. | 상태 컬럼 + 차단 설계 + 탈퇴 기능 |

**점수와 티어는 한 세트로만 전환한다.** 티어는 점수 파생값이라 둘 중 하나만 실제 값으로 바꾸면 목록의 티어와 상세의 점수가 서로 다른 구간을 가리킨다.

## 결정 사항 (확정)

- **본질문·꼬리질문 구분 없음**: 객관식 `Question`에는 `isRoot` 같은 플래그가 없다. 모든 `Question`이 동등한 독립 문항이며, 어떤 보기의 `relatedQuestionId`로 참조되는지 여부와 무관하게 문제은행에 노출된다. "본질문"·"꼬리질문"은 한 풀이 세션 안에서의 등장 순서를 가리키는 표현일 뿐이다.
- **선택지 개수**: 4개 고정(4지선다).
- **오답노트 상태·반복 횟수**: 두지 않는다. 틀린 문제 목록 + 북마크만 유지, 재풀이 시 새로운 문제 세션에서 진행. 목록 필터는 전체/북마크만 지원한다.
- **오답노트 출처(source)**: 컬럼으로 두지 않는다. 현재 오답노트를 생성하는 경로는 문제 풀이(`SolvedSessionService`/`EssaySolvedSessionService`)와 1일 1면접(`InterviewService`)이며, 셋 다 `SolvedSession`을 만드는 동일한 경로다. 자가진단·재풀이·직접저장 경로가 실제로 생기면 그때 출처 구분을 재논의한다.
- **1일 1면접 결과 저장**: 면접 결과는 별도 테이블이 아니라 `SolvedSession`(`type = ESSAY`) + `EssaySolved`에 통합 저장한다. `DailyInterview`는 포인터(`solvedSessionId`)와 진행 메타만 갖는다. → [1일 1면접 정책](#1일-1면접-정책)
- **정답 불변**: 문제 정답은 바뀌지 않으므로 정답 스냅샷을 별도로 관리하지 않는다. `SolvedMultipleChoice.answerChoiceId` 는 조회 편의용 선택 필드.
- **관리자 권한**: `User.role`(`USER`/`ADMIN`) 한 컬럼으로 표현하고, 별도 `Admin` 테이블이나 관리자 전용 로그인을 두지 않는다. 승격은 운영 DB SQL로만 하며 승격 API·도메인 메서드를 만들지 않는다. 권한 노출은 로그인 응답에만 하고 `GET /api/users/me`에는 넣지 않는다 — 클라이언트가 앱 로드 시 프로필을 조회하지 않아 쓰이지 않기 때문이다(필요해지면 그때 추가한다). → [관리자 권한 정책](#관리자-권한-정책)
