# 문항 생성 파이프라인 — 어떻게 돌고 왜 이렇게 됐나

> **구조와 근거를 적는다.** 사용법은 [`README.md`](README.md), 실제 실행 기록은 [`evidence/`](evidence/)에 있다.
> 여기 적힌 수치는 전부 그 기록에서 나온 실측이다.

## 한 줄 요약

**태그 하나를 정해 문항을 만들고, 기존 문항과 의미가 겹치면 다시 만들고, 사람이 승인하면 SQL로 뽑는다.**
LLM은 로컬 Ollama로 돌고 문항당 호출은 2회다.

---

## 1. 왜 이 구조가 됐나

처음에는 **카테고리와 난이도만** 주고 문항을 만들게 했다. 결과는
[2026-08-17 기록](evidence/2026-08-17-network-low.md)에 있다.

```
NETWORK / LOW / 5개  →  다섯 문항이 전부 쿠키
                        제목이 글자까지 같은 쌍이 둘, 둘 다 승인 통과
```

원인은 둘이었다.

1. **주제를 모델이 정한다** — "NETWORK 문항을 만들어라"라고 하면 가장 전형적인 것을 반복해서 고른다
2. **중복을 못 잡는다** — 어휘 유사도로는 말만 바꾼 중복이 안 걸린다

그래서 **주제를 밖에서 고정**하고(태그), **중복 판정을 의미로**(임베딩) 바꿨다.
그 둘이 지금 구조의 뼈대다.

> 한때 태그를 **갈래**로 더 쪼갰다. 같은 태그로 여러 문항을 뽑을 때 주제를 갈라 주려던 것인데,
> 갈래를 다 쓰면 회귀하는 상한이 생기고 297개를 손으로 유지해야 했다. **걷어냈다.**
> 같은 태그·같은 난이도로 여러 문항을 허용하고, 중복은 RAG 주입과 유사도 0.90 게이트로만 막는다.

## 2. 전체 흐름

```
tags.yml (태그 102종)
        │
        │  run.py 가 태그를 고른다
        │    --tag 인덱스              → 그 태그로만
        │    --category DB             → 사전 순서대로 넓게
        │    --category DB --per-tag 3 → 한 태그에 최대 3개씩 뭉쳐서
        ▼
┌───────────────────────── LangGraph ─────────────────────────┐
│                                                              │
│  generate ──→ validate_question ─(위반)→ generate            │
│   [LLM]              [결정적]                                 │
│                         │                                    │
│                         ▼                                    │
│                       dedup ─(중복)→ generate                 │
│                     [임베딩]                                   │
│                         │                                    │
│                         ▼                                    │
│                      rubric ──→ validate_rubric ─(미달)→ rubric│
│                      [LLM]         [결정적]                    │
│                                       │                      │
│                                       ▼                      │
│                                    review ← interrupt()      │
│                                       │                      │
└───────────────────────────────────────┼──────────────────────┘
                                        ▼
                          .work/review.json  (사람이 읽고 고침)
                                        │
                                  run.py resume
                                        ▼
                          INSERT + rubric UPDATE + question_tag
```

각 노드에서 실패하면 **되돌아가는 곳이 다르다.** 이게 설계의 핵심이다.

| 노드 | 실패 시 | 재시도 카운터 |
| --- | --- | --- |
| `validate_question` | `generate` (문항을 다시) | `generate_attempts` |
| `dedup` | `generate` (문항을 다시) | `generate_attempts` |
| `validate_rubric` | `rubric` (루브릭만 다시) | `rubric_attempts` |

각 3회까지 시도하고 넘으면 폐기한다.

> **되돌아가는 곳을 잘못 두면 영영 못 고친다.** 해설 길이 검사가 원래 `validate_rubric` 에 있었는데,
> 실패하면 `rubric` 으로 돌아가 루브릭만 다시 만들었다. 해설은 그대로라 **194자로 세 번 떨어지고
> 폐기**됐다. 문항의 결함은 `generate` 로 가야 한다.

## 3. LangGraph는 무엇을 하나

**노드 사이의 되돌아가기와 사람 개입을 관리한다.** 세 가지 때문에 쓴다.

### 3.1 조건부 되돌아가기

각 검사가 "통과 / 다시 / 폐기" 셋 중 하나를 고른다. 이걸 if 문으로 짜면 재시도 횟수와
어느 단계로 돌아갈지가 함수 여기저기에 흩어진다. LangGraph 는 그걸 엣지로 선언한다.

```python
graph.add_conditional_edges(
    "dedup", _after_dedup,
    {"rubric": "rubric", "generate": "generate", "discard": "discard"},
)
```

### 3.2 `interrupt()` — 사람 승인에서 멈추기

문항마다 사람에게 물으면 사람이 붙잡혀 있어야 한다. 그래서 **전부 승인 직전까지 돌린 뒤
멈춰 세우고**, 리뷰 파일 하나로 덤프한다. 사람이 일괄로 보고 고친 뒤 일괄 재개한다.

```
generate → ... → review  ← 여기서 멈춤. 프로세스가 끝나도 상태는 SQLite 에 남는다
                          run.py resume 이 Command(resume=...) 로 깨운다
```

### 3.3 체크포인트

노드를 지날 때마다 상태가 `.work/checkpoints.sqlite` 에 쌓인다. 중간에 죽어도 이미 만든 건
남고, 실행 중에도 밖에서 진행 상황을 읽을 수 있다.

```bash
uv run python -c "
import sqlite3
con=sqlite3.connect('file:.work/checkpoints.sqlite?mode=ro',uri=True)
for t,c in con.execute('SELECT thread_id, COUNT(*) FROM checkpoints GROUP BY thread_id'):
    print(t, '완료' if c>9 else '진행중')
"
```

**노드 함수는 LangGraph 를 import 하지 않는다.** `core/nodes.py` 는 그냥 dict 를 받아 dict 를
돌려주는 함수들이고, LangGraph 를 아는 파일은 `core/graph.py` 하나뿐이다. 그래야 노드를 단독으로
돌려볼 수 있고, LangGraph 를 걷어내도 코드가 남는다.

## 4. 태그

`vocabulary/tags.yml` 이 폐쇄집합이다. **102종.**

```yaml
- name: 쿠키와 세션
```

| 필드 | DB 에 저장되나 | 하는 일 |
| --- | --- | --- |
| `name` | **저장됨** (`question_tag.name`) | 검증·집계의 축 |

**태그당 상한이 없다.** 같은 태그·같은 난이도로 몇 개든 요청할 수 있고,
몇 개까지 갈리는지는 RAG 주입과 의미 게이트가 판정한다.

### 시드 태그와 다른 어휘라는 문제

시드 서술형 184개가 실제로 달고 있는 태그는 **504종**이고 `tags.yml` 과 **43종만 겹친다.**
504종 중 **90%가 한 문항에만 붙어 있다** — 분류 축이 아니라 문항별 키워드 목록이다.

그래서 `question_tag` 에 두 어휘가 섞여 있다. 기존 문항은 504종으로, 새 문항은 102종으로.
**태그로 집계하는 기능(오답노트 분류·추천·통계)을 붙이면 그때 막힌다.**

지금 고치지 않는 이유는 `tags.yml` 이 코퍼스를 못 덮기 때문이다. 시드 184개를 임베딩으로
최근접 배정해 보면 **64개만** 0.55 이상으로 붙고, `저장 프로시저`·`트리거`·`CAP 이론`·`DFS와 BFS`
같은 주제는 102종 안에 아예 없다. 재태깅하려면 태그를 40~60종 먼저 늘려야 한다.

## 5. RAG를 어디서 왜 쓰나

**두 군데서 임베딩을 쓴다. 하는 일이 정반대다.**

| | 쓰는 곳 | 시점 | 목적 |
| --- | --- | --- | --- |
| **RAG 주입** | `generate` | 만들기 **전** | 겹칠 만한 문항을 보여줘 **피하게** 한다 |
| **의미 게이트** | `dedup` | 만든 **후** | 그래도 겹치면 **막는다** |

### 5.1 RAG 주입 — 예방

생성 프롬프트에 "이미 있는 주제" 목록이 들어간다. 예전에는 **같은 카테고리 전부**를 넣었다 —
DB 는 28개, NETWORK 는 29개다. 목록이 길수록 초점이 흐려지고 정작 겹칠 문항이 그 안에 묻힌다.

지금은 **태그 이름을 질의로 삼아 의미적으로 가까운 5개만** 넣는다.
이번 실행에서 만든 문항도 후보에 들어가므로, 문항이 쌓일수록 목록이 갱신된다.

```
질의: "쿠키와 세션\n저장 위치, Secure·HttpOnly·SameSite, 서버 부담"
       ↓ bge-m3 코사인, 상위 5개
  - 쿠키의 주요 속성인 Secure와 HttpOnly의 역할   ← 1순위
  - 로그인 상태를 유지하는 여러 방식
  - 브라우저가 다시 요청 없이 자원을 재사용하는 방법
  - 여러 번 요청해도 결과가 같은 메서드
  - 서버가 이전 요청을 기억하지 않는다는 것의 의미
```

**효과가 관측됐다.** 위 실행에서 2번 문항은 1순위로 주입된 기존 문항(Secure/HttpOnly)을
**피해 SameSite 로 갔다.** 최종 유사도 0.666.
프롬프트도 1792자 → 1259자로 줄었다.

Ollama 가 없으면 카테고리 전체를 넣는 예전 방식으로 물러선다. 예방이 약해질 뿐 생성은 돈다.

### 5.2 의미 게이트 — 차단

만들어진 문항을 같은 카테고리의 기존 문항·이번 실행 산출물과 비교한다.
**폐기된 것도 비교 대상에 넣는다** — 빼면 방금 버린 주제를 다음 문항이 또 만든다.

```
SEMANTIC_CUT = 0.80
```

원래 어휘(3-gram 자카드) 단계가 앞에 있었으나 **뺐다.** 시드 16,836쌍을 전수 비교했더니
**어휘가 잡고 임베딩이 놓치는 쌍이 0개**였다. 반대로 임베딩만 잡은 쌍이 17개다.
판정에 기여하지 않는 단계였다.

### 5.3 왜 태그가 아니라 문항 본문을 임베딩하나

**같은 태그끼리는 태그로 구분되지 않기 때문이다.** 태그 임베딩은 같은 태그면 값이 똑같아
변별력이 0이다. 중복은 문항 수준에서 일어난다.

```
기존: B-Tree 인덱스에서 복합 인덱스의 컬럼 순서가 조회 성능에 미치는 영향
신규: 복합 인덱스 컬럼 순서와 B-Tree의 동작 방식
      → 태그는 둘 다 '인덱스' 하나. 제목·발문으로만 갈린다
```

### 5.4 컷을 어떻게 정했나

두 번 정했다.

**1차 — 사람이 만든 탐침 6개**(`similarity/probes.json`)로 눈금을 잡았다.

| 탐침 | 어휘 | 임베딩 |
| --- | ---: | ---: |
| 어순만 바꾼 중복 | 0.733 | 0.991 |
| 의미 중복 3건 | 0.061~0.133 | 0.744~0.818 |
| 대조군 2건 | 0.045~0.058 | 0.421~0.581 |

어휘에서는 **의미 중복이 대조군보다 낮게** 나온다 — 역전이라 임계값을 어디 둬도 못 가른다.
임베딩은 깨끗이 갈려 컷을 0.70 으로 잡았다.

**2차 — 실제 생성물로 다시 쟀다.** 탐침 6개는 컷 근처가 비어 보였지만
생성물은 그 구간을 채운다. DB 10문항 실측:

```
승인된 것       0.550  0.602  0.624
회색지대        0.726  0.729  0.741   ← 다른 문항인데 0.70 컷에 걸렸다
명백한 중복      0.829  0.835  0.836
```

그래서 **0.80** 으로 올렸다. 다음 NETWORK 실행에서 승인 7개가 전부 0.80 미만,
폐기 3개가 0.813~0.869 로 깨끗이 갈렸다.

## 6. LLM 없이 하는 검사

`validate_question` 과 `validate_rubric` 은 LLM 을 부르지 않는다.

| 검사 | 방법 |
| --- | --- |
| 태그가 목록 안인가 | 집합 조회 |
| 해설 길이 180~500자 | 글자 수 |
| 채점 항목 3~5개 | 개수 |
| 배점 합 = 10 | 덧셈 |
| **채점 항목이 해설에 있는 내용인가** | **포함도** |

마지막이 유일하게 기법이 필요하다. 자카드가 아니라 **containment** 를 쓴다.

```
자카드 = |A ∩ B| / |A ∪ B|    두 텍스트가 서로 얼마나 겹치나
포함도 = |A ∩ B| / |A|        짧은 쪽이 긴 쪽에 얼마나 들어있나
```

40자 항목과 350자 해설을 자카드로 재면 길이 차 때문에 항상 낮게 나온다. 포함도로 재면:

```
포함도 0.83   풀 스캔 없이 탐색 범위를 좁혀 간다          ← 해설에 있음
포함도 0.93   쓰기마다 인덱스를 갱신해야 해서 느려진다      ← 해설에 있음
포함도 0.00   샤딩 전략을 상황에 맞게 선택한다            ← 해설에 없음. 반려
```

이게 성립하는 건 **프롬프트가 "해설의 표현을 그대로 가져다 쓰라"고 요구하기 때문**이다.
지시와 검사가 짝이다. 말을 바꿔 쓰면 멀쩡한 항목도 반려된다.

## 7. 실제로 어떻게 나오나

`--category NETWORK --count 10 --per-tag 3 --rag` 로컬 실행 결과 중 하나다.

```
[TCP와 UDP-2]

제목  TCP와 UDP의 사용처 차이
발문  TCP와 UDP가 각각 어떤 상황에서 사용되는지 설명하시오.
해설  TCP는 신뢰성 있는 데이터 전송이 필요한 경우에 사용됩니다. 예를 들어 웹 브라우징,
      이메일, 파일 전송 등 데이터 손실 없이 순서대로 전달이 필요한 서비스에서 TCP가
      사용됩니다. 반면 UDP는 실시간 통신이나 저지연이 중요한 서비스에서 사용됩니다.
      영상 스트리밍, 온라인 게임, VoIP 등 데이터 손실이 허용되고 즉시 전달이 필요한
      시나리오에서 UDP가 선택됩니다. 이는 TCP의 흐름 제어와 혼잡 제어가 처리 지연을
      유발할 수 있기 때문입니다.
태그  TCP와 UDP, 실시간 통신
난이도 MEDIUM   해설 253자
```

여기에 루브릭이 붙는다.

```json
{
  "criteria": [
    { "point": "TCP는 신뢰성 있는 데이터 전송이 필요한 경우에 사용됩니다. 예를 들어 웹 브라우징, 이메일, 파일 전송 등 데이터 손실 없이 순서대로 전달이 필요한 서비스에서 TCP가 사용됩니다.", "weight": 3 },
    { "point": "UDP는 실시간 통신이나 저지연이 중요한 서비스에서 사용됩니다. 영상 스트리밍, 온라인 게임, VoIP 등 데이터 손실이 허용되고 즉시 전달이 필요한 시나리오에서 UDP가 선택됩니다.", "weight": 3 },
    { "point": "이는 TCP의 흐름 제어와 혼잡 제어가 처리 지연을 유발할 수 있기 때문입니다.", "weight": 4 }
  ],
  "followupScope": {
    "allowed": ["실시간 통신", "흐름 제어", "혼잡 제어", "신뢰성"],
    "forbidden": ["TCP/IP 계층 구조", "UDP 포트 번호 할당"]
  }
}
```

채점 항목이 해설 문장을 거의 그대로 가져온 것이 보인다. 6장의 포함도 검사가
성립하는 이유이자, 프롬프트가 그렇게 시킨 결과다.

이 JSON 이 들어가는 자리는 백엔드의 `question.rubric` 컬럼(TEXT)이다. 앱은 이걸 읽어
서술형 채점 프롬프트에 내리고, 항목별 충족 여부를 판정받아 **충족 항목의 배점 합**을 점수로 쓴다.
`followupScope` 는 같은 자리에서 꼬리질문 가드레일로 쓰인다.
→ 저장소 루트 `docs/DOMAIN.md` 서술형 루브릭 채점 정책

승인하면 SQL 로 나간다.

```sql
INSERT INTO question (title, content, type, difficulty, category, explanation) VALUES
('TCP와 UDP의 사용처 차이', 'TCP와 UDP가 각각 ...', 'ESSAY', 'MEDIUM', 'NETWORK', '...');
SET @p1 = LAST_INSERT_ID();
UPDATE question SET rubric = '{...}' WHERE id = @p1;
INSERT INTO question_tag (question_id, name) VALUES
(@p1, 'TCP와 UDP'), (@p1, '실시간 통신');
```

### 폐기되는 경우

```
TCP 연결 관리-5
  ✗ 기존 문항 'TCP 연결의 수립과 종료'와 의미 유사도 0.868로 중복이다
  ✗ (재생성) 0.869로 중복
  ✗ (재생성) 0.813로 중복
  → 폐기
```

기존 시드가 이미 그 주제를 덮고 있으면 세 번을 다시 만들어도 계속 걸린다.
**게이트가 옳게 판단한 것이고, 이런 태그는 요청하지 않는 편이 낫다.**
어느 태그가 그런지는 실행 기록의 폐기 사유로 드러난다.

## 8. 게이트가 못 잡는 것

여기까지 통과했다고 쓸 만한 문항이라는 뜻은 아니다. NETWORK 10문항을 사람이 읽어 본 결과다.

| 판정 | 개수 |
| --- | ---: |
| 그대로 사용 | 3 |
| 제목이 발문과 동일 — 수정 필요 | 2 |
| 유사도는 통과했지만 읽어 보면 겹침 | 3 |
| **사실 오류** | **1** |

**사실 오류를 아무도 안 본다.** TCP 상태 전이를 설명한 문항이 `CLOSE_WAIT` 를 능동 종료 측
상태로 적었는데(실제로는 수동 종료 측), 중복도 아니고 형식도 맞아 전부 통과했다.
로컬 8B 모델은 이런 실수를 한다.

**유사도가 사람 눈보다 관대하다.** `TCP와 UDP` 3문항은 컷을 통과했지만,
셋 다 결론이 "TCP=신뢰성, UDP=속도"로 수렴한다.

→ **`review` 단계가 형식적이면 안 되는 이유다.** 지금 구조에서 사실 검증과 내용 중복은
사람만 볼 수 있다.

## 9. 성능

로컬 `qwen3:8b`, RTX 4070 Laptop 8GB 기준.

| | |
| --- | --- |
| 문항당 LLM 호출 | 2회 (생성 1 + 루브릭 1) + 재시도 |
| 생성 속도 | 31 tok/s (GPU 96% 사용, 모델 100% VRAM) |
| 문항 하나 | 2~4분 |
| 10문항 배치 | 30~45분 |
| 임베딩 | 건당 0.24초, `.work/embeddings.json` 캐시 |

**thinking 이 시간의 상당 부분을 먹는다.** 141자를 내놓는 데 558토큰을 쓴다 — `<think>` 는
최종 응답에서 걸러지지만 생성은 그대로 한다.

느린 지점은 `rubric` 재시도다. 4개 항목의 배점 합을 10으로 맞추는 산술을 8B 모델이 어려워한다.

## 10. 검증

| 명령 | 무엇 |
| --- | --- |
| `uv run -m unittest tests.test_pipeline` | 60개. LLM 을 안 쓴다 |
| `uv run run.py generate ... --dry-run` | 대본 LLM 으로 그래프 전 분기 통과 |
| `uv run replay.py` | 기록된 문항을 **현재 게이트**로 재판정 |
| `uv run -m similarity.embeddings --calibrate` | 탐침으로 컷 판정 |

**임계값을 고칠 때 새로 생성하지 않는다.** `replay.py` 가 누적된 실행 기록 전부를 몇 초에
다시 잰다. 실제 생성이 필요한 건 **프롬프트나 모델을 바꿨을 때**뿐이고, 그때도 2~3문항이면 된다.

## 11. 저장소 밖과 닿는 곳

읽기 하나, 쓰기 하나뿐이다.

```
읽기   src/main/resources/data*.sql     시드 = 중복 비교 기준선
쓰기   --out 으로 지정한 경로            산출 SQL. 기본값 없음
```

`.work/` 는 이 폴더 안이고 `.gitignore` 대상이다. **가만히 두면 저장소 밖에 아무것도 안 쓴다.**
운영 DB 는 건드리지 않으며, 시드는 `spring.sql.init.mode: never` 라 운영에서 실행되지도 않는다.
