# 서술형 생성 프롬프트 v1 · v2 · v3 평가

**기록일 2026-08-20.** 로컬 `qwen3:8b`, OS 카테고리 같은 10태그, 난이도 MEDIUM.
세 실행의 조건을 모두 맞췄다 — **RAG 켬 · 컷 0.88 · 기준선 OS 서술형 59문항**.
프롬프트 버전만 다르다.

## 세 버전이 무엇을 바꿨나

| | 바꾼 것 | 노린 것 |
| --- | --- | --- |
| **v1** | (최초) `이미 있는 주제와 같은 것을 묻지 마라` | 중복 회피 |
| **v2** | 금지 → **차별화 축**(초점/상황/비교) + 좋은 예시 한 쌍<br>하위 초점 3개를 떠올린 뒤 안 겹치는 것을 고르는 절차 | "딴 주제로 도망" 대신 "같은 영역에서 각도 틀기" |
| **v3** | 비교 축에 **같은 층위** 제약 + 나쁜 예시<br>난이도별 발문 예시 1개씩<br>재시도에 "축을 갈아라" 지시 | 억지 비교 제거 · 난이도 일관성 · 폐기 감소 |

## 결과

```
버전    통과    폐기·실패      생성호출    초     최근접최대  최근접평균  내부최대
v1     9/10    폐기 1           12     238     0.873    0.808    0.767
v2    10/10    없음             19     350     0.874    0.803    0.792
v3     8/10    폐기 1 · 실패 1   15     291     0.869    0.797    0.785
```

- **최근접** — 기존 59문항 중 가장 가까운 것과의 유사도. 컷 0.88 대비 여유를 본다
- **내부 최대** — 같은 배치 안에서 서로 가장 겹치는 쌍
- **생성호출** — 재시도 포함 `generate` 노드 호출 수. 실제 LLM 비용

## 숫자로는 세 버전이 구분되지 않는다

최근접 최대 0.869~0.874, 평균 0.797~0.808, 내부 최대 0.767~0.792. **차이가 오차 범위다.**

폐기율도 프롬프트로 설명되지 않는다. v2가 10/10 으로 가장 좋고 v3 가 8/10 으로 가장 나쁜데,
v1 의 폐기 1건은 중복이 아니라 **태그 목록 이탈**(`모드 전환`)이고
v3 의 실패 1건은 **JSON 파싱 실패**다. 성격이 제각각이라 n=10 에서는 노이즈다.

### RAG 가 프롬프트 차이를 덮는다

같은 프롬프트를 RAG 없이 쟀을 때는 크게 갈렸다.

```
             RAG 끔        RAG 켬
v1 내부 최대   0.893        0.767
v2 내부 최대   0.750        0.792
v2 폐기       4/10         0/10
```

**오늘 얻은 개선의 대부분은 프롬프트가 아니라 RAG 몫이다**([rag-retry](evidence/2026-08-20-rag-retry.md)).
프롬프트를 고쳐 중복을 줄이려 했는데, 정작 효과는 "무엇을 피해야 하는지 보여주는 것"에서 나왔다.

## 눈으로 보면 갈린다 — 비교 대상의 층위

유사도가 못 보는 지표다. 오히려 **억지 비교일수록 기존 문항에서 멀어져 더 잘 통과한다.**

```
v1   IPC의 작동 방식과 뮤텍스의 역할               통신 기법 x 동기화 기법 — 애매
     멀티프로세스와 멀티스레드의 동작 방식과 뮤텍스의 역할    애매
v2   인터럽트의 동작 방식과 뮤텍스의 관계            하드웨어 신호 x 동기화 기법 — 성립 안 함
     IPC의 작동 방식과 뮤텍스의 차이               '차이'를 물어 더 나쁘다
     PCB의 스케줄링 정보 저장 방식과 스와핑에의 영향       비문
v3   없음
```

v3 에서 뮤텍스 억지 비교가 사라졌다. 나쁜 예시로 박아둔 `PCB와 스핀락` 조합도 안 나왔고,
같은 소재를 다룰 때 `PCB의 스케줄링 정보 저장 방식과 스와핑에 미치는 영향` 처럼
**비교가 아니라 영향 관계**로 틀었다. v2 의 비문(`스와핑에의 영향`)도 정상 문장이 됐다.

발문 형태의 다양성도 갈린다. v1 은 9개 중 7개가 `~의 동작 방식과 …` 다.
v3 는 `발생 시점`, `생성 비용의 관계`, `동시성 관리 방식과 발생 조건` 으로 갈렸다.

## 판정 — v3 를 쓴다

근거는 하나다. **유사도로 안 보이는 결함을 v3 만 없앴다.**
폐기율·속도·유사도는 세 버전이 구분되지 않으므로 선택 기준이 못 된다.
남는 판단 축이 발문 품질이고, 거기서 v3 만 층위 불일치가 0 이다.

비용은 v2 보다 싸고(호출 15 vs 19, 291초 vs 350초) v1 보다 비싸다(12, 238초).
문항 하나에 5초 더 쓰는 값으로는 납득할 만하다.

## 검증하지 못한 것

- **난이도 예시의 효과를 모른다.** v3 가 넣은 LOW/MEDIUM/HIGH 발문 예시는 이번 실행이
  전부 MEDIUM 이라 판정 대상이 아니었다. 난이도별로 발문 깊이가 실제로 갈리는지는
  `--difficulty LOW` · `HIGH` 로 따로 재야 한다
- **JSON 실패가 v3 에서만 나왔다.** 예시 3줄 + 비교 축 4줄로 프롬프트가 길어진 것이
  원인일 수 있다. 1건이라 우연일 가능성이 크지만, 재발하면 예시를 줄이는 쪽을 본다
- **층위 판정은 사람 눈이다.** 자동 검사가 없다. 이 결함은 유사도 게이트를 통과하므로
  검수에서만 걸린다
- **표본이 OS 한 카테고리 10문항씩이다.** 카테고리마다 인접 개념의 층위 구조가 다르다

## 재현

```bash
uv run run.py generate --category OS --count 10 --prompt v1
uv run run.py generate --category OS --count 10 --prompt v2
uv run run.py generate --category OS --count 10
```

실행 헤더에 조건이 찍힌다 — `프롬프트 v3+fc103de2 · RAG 켬 · 컷 0.88`.
